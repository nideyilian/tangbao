# SOP 参数与正文编辑布局分析

**日期：** 2026-09-01  
**范围：** SOP 管理中心的「SOP 库」标签页，重点分析「SOP 参数与正文」编辑区。  
**本阶段结论：** 先完成泛化作用域多选；本文只做布局分析，不在本次修改中重构参数与正文页面。

## 1. 目标与优先级

当前编辑页面的核心任务是：

1. 选择一个 SOP。
2. 快速确认名称、所属分组和说明。
3. 集中编辑 SOP 正文。
4. 保存、测试或应用当前 SOP。

其中第 3 项是主任务，正文编辑器应获得最大的稳定空间和视觉权重。名称、分组、说明、
封面、版本历史、提示词管理和应用状态都属于辅助信息或辅助操作，不应与正文争夺同等
注意力。

推荐的优先级：

| 优先级 | 模块                       | 用户需要                               |
| ------ | -------------------------- | -------------------------------------- |
| P0     | SOP 正文编辑器             | 持续阅读、修改、搜索和使用 AI 对话     |
| P1     | 保存状态与保存动作         | 清楚知道是否有未保存修改，并能立即保存 |
| P1     | SOP 名称                   | 识别当前正在编辑的对象                 |
| P2     | 所属分组、说明             | 修改归档信息和补充说明                 |
| P2     | 测试生图、应用 SOP         | 需要时快速触达                         |
| P3     | 封面、版本历史、提示词管理 | 低频操作，适合收纳                     |

## 2. 当前实现

### 2.1 管理中心外层

`SopManagementCenter` 当前使用以下层级：

```text
SOP 管理中心页头
→ 顶部 Tabs：SOP 库 / 生成元指令 / 智能生成
→ 当前 Tab 的 DialogWorkspace
```

相关代码：

- `src/features/strategy/SopManagementCenter.tsx`
- `src/features/strategy/styles.css:60-117`

页头目前包含：

- 「SOP 管理中心」标题和说明
- 导出 SOP 库
- 导入 SOP 库
- 放大模式
- 关闭

顶部 Tabs 是整个管理中心的一级导航，切换的是三个不同任务上下文，不是正文编辑器
内部的字段。因此它们仍应保留在管理中心页头下方。

### 2.2 SOP 库 Tab

`SopLibraryTab` 当前使用三栏布局：

```text
左栏：全部 / 收藏 / 最近使用 / 未分组 / 自定义分组
中栏：SOP 列表、搜索、批量操作
右栏：SOP 参数与正文
```

相关代码：

- `src/features/strategy/SopLibraryTab.tsx`
- `src/features/strategy/styles.css:86-90`

桌面默认宽度约束为：

```text
左栏 220–240px
中栏 320–390px
右栏剩余空间
```

这符合「树 / 列表 / 编辑器」工作台模式，但右侧编辑器实际还要承载正文工具栏和 AI
对话，所以它比普通属性面板需要更多空间。

### 2.3 右侧编辑区

右侧目前的结构是：

```text
编辑区标题：SOP 参数与正文
→ 状态说明和 Ctrl/Cmd+S 提示
→ 应用 SOP / 保存修改 / 提示词管理 / 选择封面 / 版本历史 / 取消应用
→ 名称
→ 所属分组
→ 说明
→ SopTextEditor
```

相关代码：

- `src/features/strategy/SopLibraryTab.tsx:384-487`
- `src/features/strategy/styles.css:367-371`
- `src/features/strategy/styles.css:2148-2160`

当前参数字段是两列网格：

- 第一行：名称、所属分组
- 第二行：说明独占整行

正文编辑器 `SopTextEditor` 本身还包含：

- 编辑工具栏
- 查找正文
- 正文文本区
- 行数和字符数状态
- AI 对话侧栏
- AI 快捷指令
- 修订提案和测试生图操作

因此，用户看到的“正文模块”实际上是一个完整工作台，不只是一个 TextArea。

## 3. 主要问题

### 3.1 主次操作混在编辑器页头

右侧页头现在同时放入六类动作：

- 应用
- 保存
- 提示词管理
- 选择封面
- 版本历史
- 取消应用

这些动作的频率、风险和作用范围不同，却共享一组横向空间。结果是：

- 正文标题和保存状态容易被按钮挤压。
- 低频动作抢占首屏空间。
- 保存动作不够稳定地成为主操作。
- 小宽度下按钮换行会进一步压缩正文。

### 3.2 名称、分组、说明没有形成紧凑元数据带

名称和分组是短字段，说明虽然可能较长，但在当前编辑场景更多是识别和补充信息。
现在说明单独占一行，造成参数区纵向占用偏大。

桌面端可以把三者合并成一条元数据带：

```text
名称（弹性） | 所属分组（固定宽度） | 说明（弹性）
```

说明不应被强制截断到不可编辑；可以采用单行输入配合横向弹性空间，窄屏时再自动
换行或折叠。

### 3.3 页头说明重复传达状态

编辑区页头已经有标题、状态说明和保存动作；正文编辑器底部还有行数、字符数和其他
状态提示；外层管理中心页头也有产品级说明。

同一层级同时存在多份说明，会增加纵向噪音。编辑区页头更适合只保留：

```text
当前 SOP 名称 + 未保存/已保存状态 + 保存按钮
```

「Ctrl/Cmd+S」可以保留为 tooltip 或帮助提示，不必长期占据一行可见文本。

### 3.4 正文和 AI 对话的空间竞争

`SopTextEditor` 的文本编辑器和 AI 对话属于同一主任务链，但两者都需要较大空间。
在右侧栏宽度不足时，正文阅读宽度和 AI 对话宽度会互相挤压。

当前代码在部分窄屏场景会隐藏正文、只保留 AI 对话，这对“修改正文”任务存在上下文
丢失风险。后续如果继续提高 AI 侧栏能力，应明确正文与对话的主次关系，而不是单纯
增加侧栏宽度。

### 3.5 外层三栏在较窄宽度下有横向溢出风险

`SopLibraryTab` 的三栏最小宽度总和较高。`styles.css` 在 `max-width: 1100px` 时将
三栏压缩，但仍保留较大的最小列宽；当前没有看到在 `max-width: 760px` 进一步把 SOP
库完整切换为单栏或 Drawer 的规则。

这不是本次布局重构的首要问题，但说明“把参数再塞进 Tab”不能作为唯一的空间解决方案。
信息架构和 pane 切换也需要一起设计。

## 4. 对用户提出方案的判断

### 4.1 名称、所属分组、说明放在一行

**建议采用，桌面端适合。**

推荐比例：

```text
名称：1.1–1.3fr
所属分组：0.6–0.8fr
说明：1.2–1.5fr
```

约束：

- 名称和说明都必须保留可见 label。
- 所属分组不能被压缩到无法识别。
- 说明允许单行编辑，内容过长时保留输入框横向滚动或显示末尾内容。
- 低于编辑器可用宽度阈值时，三者自动变为两行，而不是继续压缩字体。

### 4.2 去掉顶部页头

**不建议直接删除整个页头。**

外层页头承担了管理中心的定位、关闭、导入导出和放大模式。直接删除会带来：

- 管理中心失去清晰的窗口身份。
- 全局动作没有稳定归属。
- 关闭和放大入口需要迁移到不明显的位置。

**建议做成紧凑页头：**

- 保留标题。
- 删除或弱化「统一管理 SOP、分组和生成元指令」这类说明。
- 导入、导出、放大收进更多菜单。
- 保留关闭按钮。
- 页头高度从当前约 70px 级别缩减到约 48–56px。

### 4.3 把右侧参数组件直接放到 Tab 栏

**不建议把参数组件直接放进一级 Tabs。**

当前 Tabs 切换的是：

- SOP 库
- 生成元指令
- 智能生成

它们是三个并列工作区。把名称、分组、说明放进 Tab 栏，会把对象属性和工作区导航
混成同一层级，用户也会误以为参数是全局 Tab 状态。

更合理的做法是：

```text
一级 Tabs 保留
→ SOP 库内部三栏保留
→ 右侧编辑器顶部增加紧凑元数据带
```

如果将来需要进一步收缩参数，最多在右侧编辑器内部增加一个低频的“更多设置”折叠区，
不要把正文编辑器藏到 Tab 后面。

## 5. 推荐目标布局

### 5.1 外层结构

```text
紧凑管理中心页头
→ 一级 Tabs
→ SOP 库三栏工作区
```

外层不承担具体 SOP 参数。

### 5.2 右侧编辑器结构

```text
当前 SOP 名称                         [保存] [更多]
已保存 / 有未保存修改

[名称________________] [所属分组____] [说明________________________]

正文编辑器
├─ 正文工具栏
├─ 正文区域
└─ AI 对话 / 提案区
```

「更多」中收纳：

- 应用 SOP
- 提示词管理
- 选择封面
- 版本历史
- 取消应用

如果当前 SOP 已应用，可以在名称旁用短状态 Badge 表达“使用中”，不需要额外占用一个
大按钮位置。

### 5.3 保存策略

当前已有 800ms 自动保存、手动保存和 `Ctrl/Cmd+S`。建议保留，但视觉上只突出一个
保存状态：

| 状态             | 显示                |
| ---------------- | ------------------- |
| 无修改           | 已保存              |
| 修改等待自动保存 | 正在保存            |
| 自动保存完成     | 已保存              |
| 名称或正文为空   | 无法保存 + 就近提示 |

手动「保存修改」仍然保留，作为显式恢复路径；不要再增加第二个同义保存入口。

## 6. 分阶段改造建议

### 第一阶段：低风险压缩

只调整 `SopLibraryTab` 和对应 CSS：

1. 名称、所属分组、说明改为桌面单行元数据带。
2. 编辑器页头只保留标题、保存状态、保存按钮。
3. 低频动作收进更多菜单。
4. 保留 `SopTextEditor` 的正文与 AI 对话结构不变。

验证重点：

- 自动保存和 `Ctrl/Cmd+S` 不变。
- 切换 SOP 前的未保存确认不变。
- 当前应用状态不丢失。
- 正文编辑器获得更多高度。

### 第二阶段：正文空间强化

在第一阶段稳定后再考虑：

1. 右侧编辑器采用明确的 `min-height: 0` 和单一主滚动区。
2. AI 对话侧栏设置可收起状态，但保留可发现的入口。
3. 正文工具栏和 AI 快捷指令区分别限制最大高度。
4. 让正文文本区成为右侧唯一的弹性增长区域。

验证重点：

- 正文不会因为快捷指令或消息增长而被挤出可视区。
- AI 对话收起和恢复不丢草稿。
- `documentId` 对应的 AI 对话历史仍能恢复。

### 第三阶段：窄宽度结构调整

如果产品仍需要窄屏使用，再单独处理：

1. 三栏切换为「列表 → 编辑器」逐级进入。
2. 分组侧栏改为 Drawer 或折叠导航。
3. 不让三栏通过横向滚动长期承载主编辑任务。

该阶段应作为结构改造单独验收，不和第一阶段的桌面压缩混在一起。

## 7. 暂不建议的方案

- 删除整个管理中心页头。
- 把名称、分组、说明放进一级 Tab 导航。
- 把正文放到“正文 / 参数”二级 Tab，并默认隐藏正文。
- 将所有低频操作继续平铺在编辑器页头。
- 仅靠缩小字号和减少 padding 解决空间问题。
- 把正文、AI 对话、版本历史、提示词管理全部塞进同一个滚动容器。

这些方案会降低发现性、增加上下文切换，或让正文不再是主工作区。

## 8. 改造验收标准

### 桌面主视图

- 名称、所属分组、说明在同一行显示，字段仍有可见 label。
- 正文编辑器是右侧最大、最稳定的弹性区域。
- 保存状态在 1 秒内可识别。
- 保存按钮只有一个主入口。
- 低频操作可在两次点击内完成。
- 右侧编辑区不出现无意义的第二个页面级滚动条。

### 行为回归

- 切换 SOP 时保留未保存确认。
- 自动保存仍然保存名称、分组、说明和正文。
- `Ctrl/Cmd+S` 仍能立即保存。
- AI 对话草稿、历史和修订提案不因布局调整丢失。
- 应用、测试生图、版本恢复和提示词管理入口行为不变。

### 响应式

- 1024px 左右仍能看清正文和保存动作。
- 窄宽度下字段换行，不通过极小字号硬塞一行。
- 正文和 AI 对话至少有一个始终可见，不能出现双双被裁切。

## 9. 结论

推荐路线是：**保留一级 Tabs 和三栏工作区，压缩外层页头，参数改成右侧编辑器顶部的
单行元数据带，低频动作收进“更多”，把正文编辑器作为唯一弹性主区域。**

这样能直接回应“突出编辑大模块、缩小其它参数区域”的目标，同时不破坏当前的
SOP 库 / 生成元指令 / 智能生成信息架构，也能保留自动保存、版本历史和 AI 对话这些
已有能力。
