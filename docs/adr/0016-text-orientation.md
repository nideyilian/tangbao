# 0016 文字层支持竖排（`orientation`）：换行 = 换列，框不参与折列

- **日期**：2026-09-22
- **状态**：生效中（已实现，TB-097）
- **决策者**：杰哥（产品负责人）
- **相关**：[0006](0006-watermark-identifier-and-transfer.md)（标识符叠加）、TB-096、R-83、R-85

## 背景

杰哥报障（附截图）：竖排合规水印的第一行是 `★该` —— 标识符与首字并排。

排查发现两件事：

1. 产品里**没有「文字方向」参数** —— `CompositeV2TextLayer` 无方向字段、图层面板「内容」组无控件、
   全仓 grep `竖排 / vertical / writing-mode` 只命中素材库的横竖筛选与策略提示词里的文字描述。
   竖向文案当时的唯一做法是**一个字敲一个换行**。
2. 这个手写写法有两个代价：改一个字要把后面所有字往后挪；而且竖排里「一行」就是**一个字的格子**，
   标识符贴到首行行首必然与首字并排（就是这次的报障现象）。

杰哥看过方案后拍板：做。

## 决策

给 `CompositeV2TextLayer` 加**可选**字段 `orientation?: 'horizontal' | 'vertical'`：

- **判定**：只有 `orientation === 'vertical'` 才是竖排，其余（缺省 / 脏值 / 老数据）一律横排 ——
  与 `withIdentifier` 同一口径（正向字段、缺省即老行为），**因此不需要任何归一化或持久化迁移**，
  预设包导入导出也不用改（图层是整体透传的）。
- **排版**：换行符 = **换列**，列内逐字向下；`lineHeight` = **列距**、`letterSpacing` = 列内**字间距**；
  多列以对齐锚点为中心向两边排（与横排多行的 y 算法同构，所以 `align` 仍读作「这一块贴哪边」）。
  **不做自动折列。**
- **「一个字一行」是竖排的另一种写法**：竖排渲染前先把它折成一段（`resolveVerticalColumns`），
  渲染与测量**共用这一个函数** —— 否则那几个换行会被当成换列，把竖排排成横着的一排。
- 框（`position.width/height`）仍**只用于定位**；`measureCompositeTextBox` 竖排时与横排
  **逐项对调**（宽 = 列数 × 列距、高 = 最长列），让「自动适应」之后的锚点仍对得上。

## 理由

**为什么不做自动折列**：折列需要一个可信的列高约束，而框是历史数据（R-83：旧版文本层的框是
手拖的 / 铺满画布的，且算不进渲染时才叠加的标识符）。拿它折列就是把「差一像素」放大成「多一列」。

**为什么不用布尔开关**（`vertical?: boolean`）：`false` 与「老数据没有这个字段」在界面上长得一样，
会被读成「被谁关掉了」；枚举里两个值都是明确的选择。

**为什么把「手写竖排」的识别放在文案形状上**（`isVerticalText`：≥2 行且每行只占一个字符）：
存量数据都是手写竖排的，认不出来它们就会在切到竖排时被排成横着的一排。
代价是「两行两字的短文案」（`优惠\n限时`）也会被当竖排 —— 但那本来少见，且那样排更接近竖排，不违和。
判据用 `Array.from` 数**字符**：emoji 是代理对，按码元数会漏。

## 后果

- 正面：竖向文案不用再手敲换行；标识符自动成为第一格（文案上方，TB-096 也已就位）；
  改动**不需要迁移**，老预设包导入后行为不变。
- 代价 / 知情取舍：
  - 不自动折列 ⇒ 一列装不下要自己敲换行换列；
  - 竖排字宽按 `fontSize` 近似（框只定位，不值得为它逐字 measure）；
  - 手写「一字一行」与真竖排**渲染结果一致**，但数据形状不同 —— 这正是 R-85 记的那类
    「两条路径产出同一份输出」：写守卫时必须挑**只有新路径才给得出**的判据（本例是 y 步进）。
- 对后续代码的约束：竖排的三个口径（换列 / 列距 / 字距）与横排**逐项对称**，改一边就要改另一边；
  列的切分**必须**走 `resolveVerticalColumns`（渲染与测量共用，别各写一遍）。
