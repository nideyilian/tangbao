# 0004 参数继承语义：`undefined` = 继承、空值 = 显式覆盖；`distribution` 整份替换

- **日期**：2026-09-18
- **状态**：生效中
- **决策者**：杰哥（产品负责人）+ 实现层取舍

## 背景

参数按 `collectionId` 逐级浅合并（方向 → 产品 → 产品线 → 全局默认）。
一旦支持"继承 + 可覆盖"，就必须回答三个语义问题，而它们**在界面上无法靠直觉区分**：

1. 一个字段**没表态**和**明确表态为空**，是不是一回事？
2. 多级覆盖时，**写回**要不要连同未改动的兄弟字段一起写？
3. 某些字段能不能"只继承一半"？

这三个问题各自都能造出"界面上推理不出来的组合"，且都是**静默错误**
（用户看到的与实际生效的不一致），因此必须以文字固定语义。

## 决策

1. **`undefined` = 继承，空值（`''` / `[]` / `null`） = 显式覆盖。**
   判据一律 `=== undefined`，**禁止用 `length` 或真值判断**。
2. **继承态下第一次改动必须"物化"**：取**生效值**做增删再写回，不能直接写结果数组。
3. **`distribution`（分发排期）整份替换，不逐字段继承。**
4. 参数层的键**刻意不随节点删除而清理**（保守方向）。

## 理由

- **问题 1**：`outputDir: ''`（产出到根）与 `watermarkPresetIds: []`（明确不加水印）都是**真实意图**。
  用真值判断（`||`）会把它们当成"没给"，回退到父级 —— 用户"关掉水印"的操作会**静默失效**。
  所以解析必须 `??`。这也是 `RISK.md` R-15。
- **问题 2**：默认分组下若直接写结果数组，"少一个水印"会被表达成"一个都不要"。
  用**生效值**做增删，首次改动天然就是"本级自定义"，语义自洽。
- **问题 3**：`distribution` 的排期由**起始日期 + 天数**共同决定，
  拆开逐字段继承会拼出**界面上推理不出来的组合**（例如父级给了起始日期、本级给了天数）。
  整份替换让"这一份是谁配的"永远可回答。
- **问题 4**：删除节点时清理参数可以省空间，但一旦树被复原（撤销 / 重新导入 / 内置结构补齐），
  参数就永久丢失。**保守方向**成本只是少量孤儿记录，收益是可逆。

## 后果

- **正面**：用户能区分"我没配"和"我明确配了空"；产出目录与水印的生效结果可推理、可回滚（「恢复继承」）。
- **代价 / 知情取舍**：
  1. 树上**看不出** `undefined` 与 `[]` 的区别（只剩「恢复继承」出口的有无）——
     这是为了"不挂标注标签"的界面简洁性做的交换。
  2. 会产生少量孤儿参数记录（节点已删、参数仍在）。
  3. `distribution` 整份替换意味着**不能只改其中一个字段** —— 表单必须一次性提交完整配置
     （`PostprocessDistributionFields.tsx` 是面板与项目树参数弹窗**共用**的一份表单，就是为了保证这点）。
- **对后续代码的约束**：
  - 新增可继承字段时，先问"空值是否有语义"。有 → 必须 `??`；无 → 可以用 `||`，但要在代码里写明理由。
  - 分发的 early return **只看 `enabled`**，不能用 `isPostprocessDistributionActive`
    （那个还要求日期合法）—— 用它做守卫会把"开了开关但日期没填"变成**静默什么都不做**，
    而这恰恰是最需要报错的情形。
  - 新增「按渠道」这类覆盖入口时，继承态首次改动同样要物化。

**证据**：`features/projectTree/params.ts`、`lib/postprocessDistribution.ts`、
`PostprocessDistributionFields.tsx`、`params.test.ts`（含"空数组 = 明确不加水印"专门用例）。
