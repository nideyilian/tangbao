# 0023 嵌入图转视频引擎：复用独立 Python 引擎，参数挂项目树

- **日期**：2026-09-26
- **状态**：**生效中（已实现第一期）**
- **决策者**：杰哥（产品负责人）
- **相关**：TB-135、R-108、R-109；`electron/image-video/`、`src/features/imageVideo/`；
  复用 [0011](0011-postprocess-global-vs-node-scope.md)（全局基线 vs 节点覆盖的分层）

---

## 背景

杰哥 2026-09-26 的需求原话：

> D:\AAA\image-to-video，我要把这个程序嵌入当前项目，用于在导出图片后再用导出的图片进行图转视频，
> 同样要在表格可以填参数和设置，依旧以树为准。

被嵌入的程序（`D:\AAA\image-to-video`，「图转视频极速版」）已经改造成两层：Tauri 2 + React 的壳，
加上一个 PyInstaller 冻结的 Python 引擎（约 106MB，NDJSON over stdin/stdout，协议号 1）。
**壳不要，引擎可整块复用** —— 它有 33 种转场、39 种画面动态效果、BGM、多层水印、分辨率/帧率/码率、
暂停取消与进度，还有单帧效果预览，全是现成的。

杰哥当场定的三条口径：

1. **输入源 = 中控台产出的导出目录**（后处理落到导出位置的那批图）；
2. **触发 = 导出完自动接着跑**（默认关，树上按方向开）；
3. **体积 = 引擎和 ffmpeg 都塞进安装包**。

## 决策

### 1. 复用引擎 exe，不重写、不走云端

三条路线摆过（复用引擎 / 用 Node + ffmpeg 重写 / 走云端图生视频 API），选复用引擎：

- **重写不划算**：`src/render/` + `src/core/` 是 4000 多行图像处理代码，重写工期以月计，
  而且做不到与现有效果一致（用户会比）。
- **云端不是同一件事**：按次付费、断网不能用，出来的也不是这个程序的手感。
- **代价是体积**：安装包从 125.9MB 涨到约 215–225MB（参照：原程序自己带同一个引擎，NSIS 包 107.3MB）。

**ffmpeg 不需要额外捆**：引擎内部的 `imageio_ffmpeg` 自带一份 7.1（解压后 87MB）。
本机把 PATH 清空实测过，它会回退到自己那份（`ffmpeg_available: true`）。
但查找顺序是**先 PATH 后自带**，所以糖包必须把「实际用的是哪一份」显示出来（见 R-108）。

### 2. 引擎 exe **不进 git**，构建时取件

111,487,840 字节 = 106.3 MiB，**超过 GitHub 单文件 100 MiB 上限**，push 会被拒。
原程序也是 gitignore 掉、CI 现场用 PyInstaller 构建的。

所以：`scripts/fetch-image-engine.mjs` 在构建前把引擎取到 `resources/image-engine/`（该目录被 gitignore），
由 `electron-builder.cjs` 的 `extraResources` 放进 `process.resourcesPath/image-engine/`。
取件有三条来源（本机源 / `TANGBAO_ENGINE_SOURCE` / `TANGBAO_ENGINE_URL`），
**缺文件时 `beforePack` 直接让构建失败** —— 静默出一个「能装能开能生图、只有跑视频才炸」的包是最坏结果（R-109）。

### 3. 参数挂项目树，沿用后处理那套继承链

与 [0011](0011-postprocess-global-vs-node-scope.md) 完全对位：全局基线一份
（`useImageVideoStore.globals`），节点覆盖按 `AssetCollection.id` 存进**既有的**
`useProjectTreeParamsStore`（`ProjectNodeParams` 加一个 `imageVideo` 字段 —— 那个「包一层对象」
本来就是为接入新模块参数留的）。

**留空 = 继承** 的口径与后处理一字不差：节点覆盖里空串 / 空值一律从结果里删掉（= 没表态），
逐级浅合并（方向 → 产品 → 产品线 → 全局）。

**转场与画面效果合成一列下拉**，不是「模式 + 样式」两列：用户想的是「用哪种转场」，
所以下拉直接并列 `不用` / `随机` / 33 种具体转场名，选中具体名字即
`use_transition=true, random_transition=false, transition_type=名字`。少 4 列宽度。

### 4. 自动出视频挂在**后处理产出之后、分发之前**

分发（`lib/postprocessDistribution.ts`）会**把产出文件夹按排期日搬走**；搬完之后
「这个方向的一批图」就散在好几个日期目录里，而一个视频没法跨那么多目录取图。
所以自动触发点在 `store.ts` 的方向级收尾处（`recordDirectionPostprocessHistory` 之后）。

由此带来一条明确的组合限制：**开了分发时，视频用的是分发前的那批图**。
另外自动触发是 fire-and-forget + **串行队列**（`autoTrigger.ts`）：视频渲染要几分钟，
既不能拖住后处理收尾，也不该多方向一起涌进来把 CPU 占满。

### 5. 引擎常驻，收工走整棵进程树

引擎是 onefile，每次启动要解压 106MB；而且它自己带任务队列。所以**常驻**：
按需启动一次，应用退出时才收工。

⚠️ 引擎跑渲染时会 spawn 自己（`exe --legacy-worker`），糖包起的进程**还有孙子**。
所以退出走**两层**：`before-quit` 优雅关闭 + `will-quit` 同步 `taskkill /T /F` 兜底（R-108）。

### 6. IPC 只开**白名单方法**

引擎暴露 60 多个方法（含 `library_*`、`jianying_*`），而它**不认识糖包的路径白名单**。
所以透给渲染进程的是一张显式方法表（`engine-ipc.ts` 的 `ALLOWED_METHODS`），
别的一律拒 —— 开个通用 `call(method, params)` 等于开了个能绕过糖包白名单读写任意目录的后门。

## 后果

**好**

- 视频能力当天就可用，效果与那个程序一致（同一份引擎）。
- 参数按方向各配一份、逐级继承，与后处理同一套心智；导出与视频共用同一棵项目树。
- 安装包体积一次性涨到位，之后加参数不再涨。

**坏 / 代价**

- 安装包从 125.9MB 涨到约 215–225MB；CI 构建时间变长。
- 引擎是**另一个程序**，版本要单独跟：升级引擎 = 换 `engine.json` 里的 sha256，糖包仓库看不见 diff。
- 引擎自带水印与 BGM 体系与糖包的水印库是**两套**，第一期全部显式关掉，不做桥接。
- 「开了分发」与「自动出视频」组合时，视频用分发前的图 —— 已写进注释与界面说明。
