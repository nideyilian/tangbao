# 0009 参数模型评估（**已作废** —— 前提理解错误，见 0010）

- **日期**：2026-09-20
- **状态**：**已被 [0010](0010-param-center-scope-correction.md) 取代**
- **作废原因**：杰哥指出本 ADR 对本项目的**产物结构理解有严重偏差**。
  我把「渠道 / 尺寸 / 横竖」当成了「树结构的一部分」，并据此提议「删掉冗余层级」。
  实际上**它们本来就不是树的层级**，树结构本身没有问题。
  本文件保留仅为记录这次误判，**不要按它执行**。

## 错在哪（便于对照）

| #   | 原文主张                                                            | 错在哪                                                                                                     |
| --- | ------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| 1   | 「61 个方向 × 25 个目录分叉 × 56 个水印分叉」→ 据此论证「树太复杂」 | **数据是对的，推论是错的**。分叉是**渠道**维度造成的，而渠道本来就不在树里 —— 拿它论证「树冗余」是逻辑错位 |
| 2   | 「参数编辑不需要树，树降级为批量编辑表格里的一个列」                | 属性错配。树的层级是**业务归属**（产品线/产品/方向），我把它当成 UI 控件来评价，没搞清它承担什么           |

## 保留下来的、仍然有效的部分

以下几条与理解偏差无关，仍然算数（已迁到 ADR-0010）：

- `PostprocessNodeOverride` 有 10 个可覆盖字段（已实测确认）。
- `paramSchema.ts` 有 11 个参数项（8 `both` + 1 `node` + 2 `global`，已实测确认）。
- 存储形状 `Record<collectionId, {postprocess}>`；改字段集**零迁移成本**、`version` 不用 bump。
- **R-63**（字段集收窄时旧数据节点级值静默消失）—— 独立成立。

## 教训

**评估别人的系统时，先问「这个结构是为谁服务的」，再评价它是否冗余。**
本次看到「三级树 + 每节点参数」就直接套了「层级太深 → 应该扁平化」的通用模板，
没有先确认：**树的每一级承载什么业务含义、哪些东西本来就不属于树**。
结论：**我把「不属于树的维度」误当成了「树的冗余层级」，然后提议删掉一个本来就不存在的问题。**
