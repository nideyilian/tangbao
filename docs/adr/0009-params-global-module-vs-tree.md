# 0009 参数模型：从「项目树继承」回到「全局模块 + 项目×方向索引表」

- **日期**：2026-09-20
- **状态**：**提案中（待杰哥裁决）**
- **决策者**：杰哥（产品负责人）
- **相关**：ADR-0001（统一项目树）、ADR-0003（按渠道覆盖范围）、ADR-0004（继承语义）、TB-049、TB-014

## 一句话

杰哥要求「把项目树拓展为全局参数设置模块、后处理只留必要项」。**调研结论与要求有一处根本冲突**：
现行参数模型的复杂度**不是设计过头，而是被真实业务数据逼出来的**（61 个方向 × 25 个目录分叉 ×
56 个水印分叉）。因此本 ADR **不建议推倒树形结构**，而是提出「**结构归结构、参数归参数**」的
单向解耦 + 一张**项目×方向索引表**作为参数的统一主界面。

## 一、现状盘点（先看清有什么，再谈改什么）

### 1.1 两棵树，各司其职

| 树                     | 载体                               | 存什么                                | 谁在用                                   |
| ---------------------- | ---------------------------------- | ------------------------------------- | ---------------------------------------- |
| **结构树**（唯一主源） | `useAssetLibraryStore.collections` | 产品线 → 产品 → 方向 的名称与层级     | 左侧栏 / SOP 分组 / 后处理 / 水印 / 导出 |
| **参数层**（覆盖切片） | `useProjectTreeParamsStore.params` | `Record<collectionId, {postprocess}>` | 后处理执行、水印归属、预设转移           |

参数层**刻意独立成 store** 而不是给 `collections` 加列 —— 见 `features/projectTree/types.ts:11-13`：
collections 是目录元数据（动它要改 SQLite schema + 迁移），参数是应用配置，两者生命周期与备份诉求不同。**这个决策是对的，本次不推翻。**

### 1.2 后处理现在到底有多少个参数

`paramSchema.ts:147-247` 共 **11 项**，按作用域分：

| scope    | 项                                                                         | 数量 |
| -------- | -------------------------------------------------------------------------- | ---- |
| `global` | 媒体表、产出预览                                                           | 2    |
| `both`   | 媒体勾选、画面方向、命名模板、创作者、输出目录、纯净版伴随、分发、水印归属 | 8    |
| `node`   | 参与自动后处理                                                             | 1    |

再加上**按渠道第二层**（`byMedia` 只开 `outputDir` / `watermarkPresetIds`，ADR-0003），
以及**继承四层**（方向 → 产品 → 产品线 → 全局默认）。

⇒ 单个字段的生效值，最坏要推理 **4 层 × 2 维度 = 8 个位置**。

### 1.3 「冗余层级」的真实来源

`PostprocessNodeOverride`（`lib/postprocessMedia.ts:335-358`）有 **10 个可覆盖字段**。
但从**实际业务数据**看，其中只有两项真的需要逐节点/逐渠道差异：

- ADR-0003 记录《输出位置明细-独立版》61 个方向：**25 个目录按渠道分叉、56 个水印按渠道分叉**。
- 其余 8 个字段（`namePattern` / `creator` / `direction` / `selectedMediaIds` /
  `autoCompanionClean` / `distribution`）**没有任何业务证据表明它们逐方向不同**。

**这就是「冗余」的准确位置**：不是树错了，是**可覆盖字段集开得比业务需求宽**。

## 二、逐条回应你的三个要求

### 要求 1：把项目树拓展为全局参数设置模块

**判断：方向对，但要拆成两件事，不能一锅端。**

「项目树」这个词在系统里其实指**两个东西**，混在一起才是入口混乱的根源：

| 名字                       | 是什么                             | 该不该成为「全局参数模块」 |
| -------------------------- | ---------------------------------- | -------------------------- |
| `ProjectTreeWorkbench`     | 结构管理表格（增删改名、启用范围） | ❌ 它是**结构**，不是参数  |
| `PostprocessSettingsModal` | 后处理参数编辑                     | ✅ 但它现在只服务后处理    |

**建议**：新增一个**全局参数中心**（`ParamCenterModal`），把「**结构**」与「**参数**」在同一屏
分成两个 tab / 两栏，但**底层仍是两棵树、两个 store**。结构 tab 就是现在的
`ProjectTreeWorkbench` 原样搬进来；参数 tab 是下面 §三 的索引表。

> ⚠️ **不建议**把参数并回 `collections` 表。理由：① 要动 SQLite schema + 迁移（风险远大于收益）；
> ② 参数需要「导出备份 / 整份导入 / 删节点保留参数」三种 collections 不需要的语义（ADR-0004 决策 4）。

### 要求 2：后处理只保留必要设置项

**判断：可行，但「必要」要按证据定，不能按感觉定。**

我按 ADR-0003 的证据口径，把 11 项分成三类：

| 处置            | 项                                                           | 依据                                                         |
| --------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| ✅ **必留**     | 媒体勾选、画面方向、输出目录（含按渠道）、水印归属、参与开关 | 有 61 方向真实数据支撑（25 / 56 分叉）                       |
| ✅ **必留**     | 命名模板、创作者                                             | 产出文件名刚需，且是 TB-049 已确认要加预览的项               |
| ⚠️ **上收全局** | `autoCompanionClean`、`distribution`（分发排期）             | **无任何逐方向差异证据** → 从 `PostprocessNodeOverride` 收回 |
| ⚠️ **上收全局** | `selectedMediaIds`（节点级渠道勾选）                         | 启用范围已由「参与开关」表达，再叠一层渠道勾选属重复控制     |
| ✅ **保持全局** | 媒体表、产出预览                                             | 本来就是 `scope: 'global'`，无需改                           |

**关键收益**：`PostprocessNodeOverride` 从 **10 字段 → 5 字段**（`enabled` /
`outputDir` / `byMedia` / `watermarkPresetIds` / `namePattern`）。

> ⚠️ **`direction` 需单独讨论**：它现在是 `both`，但 `resolveProjectNodePathNames`
> （`params.ts:68-79`）已经把**节点在第 3 层的名字**当作 `{direction}` token。
> 也就是说「方向」这个概念**在结构里已经存在**，配置项 `direction`（尺寸方向推导）与它是**两件事**，
> 名字撞车才是用户困惑的来源。建议把配置项改名为「**产出尺寸方向**」并上收全局，
> 方向名继续只从结构树取。**这条要你确认**（见 §五 待裁决 2）。

### 要求 3：后处理是否还需要树形结构？

**判断：参数编辑不再需要树；但树不能删，要改成「选择器」。**

三者要分开看：

| 用途                   | 需要树吗   | 说明                                                               |
| ---------------------- | ---------- | ------------------------------------------------------------------ |
| **表达继承关系**       | 需要       | `direction → product → line → global` 是**真实存在的层级**，删不掉 |
| **作为参数编辑的导航** | **不需要** | 77 个节点逐个点开配，效率极低 —— 这正是你感到「层级冗余」的原因    |
| **作为结构的唯一主源** | 需要       | 左侧栏 / SOP / 导出都依赖它，动它会引发全局震荡                    |

⇒ **结论：树保留为「继承语义的载体」，但从「主导航」降级为「批量编辑表格里的一个列」。**

## 三、推荐的组织方式：项目×方向索引表（不是扁平字典）

### 3.1 为什么不是纯扁平字典

你提的「扁平化配置 / 按项目+方向索引的字典」方向是对的，但**纯扁平会丢掉继承**。
如果给每个方向存一份完整参数，就会出现：

- 改一条产品线的输出目录 → 要遍历它下面所有方向改一遍（**批量改动退化成循环写**）；
- 新加一个方向 → 参数从哪来？无人回答（**新节点无默认值**）。

⇒ 正确形态是：**索引表（给人看的编辑面）+ 继承链（给机器算的真相）**，两者同一份数据两种投影。

### 3.2 参数模型（重构后）

```
┌─ 全局基线（默认值层）────────────────────────────────┐
│ PostprocessMediaConfig  ← 现有结构不动，字段数不变     │
│   media / selectedMediaIds / direction(→产出尺寸方向) │
│   outputDir / mediaOutputDirs / namePattern / creator  │
│   watermarkPresetIds / autoCompanionClean / distribution│
└───────────────────────────────────────────────────────┘
                       ▲ 继承（undefined = 继续向上找）
┌─ 节点覆盖（按 collectionId 索引）──────────────────────┐
│ PostprocessNodeOverride  ← 10 字段 → 5 字段            │
│   enabled? / namePattern? / outputDir?                │
│   watermarkPresetIds? / byMedia?                      │
└───────────────────────────────────────────────────────┘
```

**存储形状完全不变**（`Record<collectionId, {postprocess}>`），
变的只是 **`PostprocessNodeOverride` 的字段集**和**消费端的界面**。⇒ **零迁移成本**。

### 3.3 数据流（重构后）

```
                 ┌──────────────────────────┐
                 │  ParamCenterModal        │
  结构 tab ──────┤  ├─ 结构表（原 ProjectTreeWorkbench）
                 │  └─ 参数表 ★ 新增          │
                 └───────────┬──────────────┘
                             │ 行 = 产品线/产品/方向（展平 + 缩进）
                             │ 列 = enabled | outputDir | 按渠道 | 水印 | 命名
                             ▼
              resolveProjectPostprocessSlice()   ← 不改
                             │
              applyPostprocessOverride()          ← 只删字段，逻辑不动
                             │
                             ▼
        每行旁边直接显示「本级 / 继承自 X」徽章（复用 ProjectTreeTableRow 现有字段）
                             │
                             ▼
                    taskPostprocess.ts             ← 不改
```

### 3.4 主要代码调整点

| #   | 文件                                                                | 改动                                                                                        | 规模   |
| --- | ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- | ------ |
| 1   | `lib/postprocessMedia.ts` `PostprocessNodeOverride`                 | 删 5 个字段（`selectedMediaIds`/`direction`/`creator`/`autoCompanionClean`/`distribution`） | 小     |

| 5   | `features/postprocess/PostprocessParamPanel.tsx`                    | 右栏退化为「全局基线编辑」；节点态只留 5 项                                                 | 中     |

## 四、兼容性（这是本次最关键的一环）

**旧数据里一定存在**用户已经在节点上配了 `distribution` / `autoCompanionClean` 的情况。
字段上收全局后，这些残留值**不能直接丢弃**，否则用户配置静默消失（正是 R-47 那类"静默失效"）。

### 处置口径（三选一，**我推荐 C**）

| 方案  | 做法                                                                         | 评价                                    |
| ----- | ---------------------------------------------------------------------------- | --------------------------------------- |
| A     | 直接删，不管旧值                                                             | ❌ 用户配置静默消失，不可接受           |
| B     | 保留字段在类型里（只是 UI 不显示）                                           | ❌ 留脏字段，读的时候还是要想"要不要用" |
| **C** | **归一化时把节点级值「提升」到全局基线，节点级记录删除；并在升级提示里告知** | ✅ **推荐**：用户配置保留，语义不丢     |

**方案 C 的落地**：

```ts
// params.ts · normalizePostprocessNodeParamsMap 内
// 节点级 autoCompanionClean / distribution 是旧格式，读到就丢弃（不报错），
// 由 storePostprocessMedia 的 migrate 负责"取链上最深的一个值提升到全局"。
```

具体来说，`storePostprocessMedia` 的 `migrate` 需要读一次 `projectTreeParams` 的旧数据
—— 但 **store 之间不该互相依赖**。更干净的做法是：
在**应用启动时的一次性迁移**里做（`electron/` 或 `store.ts` 的 hydrate 之后），
按「深度优先取最后一个声明的值」提升到全局，并在 `localSettings` 里落一个
`paramsPromotionDone: true` 标记，只跑一次。

> ⚠️ 这一步**风险等级 R**（会改用户数据）。必须先备份 + 写成可回滚的一次性脚本，
> 且**运行前要求用户确认**（按 `RISK.md` 的 R-03 口径）。

## 五、待杰哥裁决（3 点，定了我才动手）

### 裁决 1：是否接受「结构树保留、只把参数做成索引表」？

- **接受** → 我按 §三 全量实现（改动 10 处，其中 1 处较大）。
- **不接受，坚持要扁平化** → 需要接受两个代价：① 改产品线目录要批量循环写；
  ② 新增方向无默认值。我会按这个方向做，但要先加一条 ADR 记录取舍。

### 裁决 2：「方向」这个名字撞车怎么解？

现在有两件事都叫「方向」：

1. **结构树第 3 层节点的名字**（`{direction}` token 取它）
2. **配置项 `direction`**（`landscape` / `portrait` / `square`，决定产出哪些尺寸）

建议 **2 改名为「产出尺寸方向」并上收全局**。是否同意？

### 裁决 3：旧数据里的节点级 `distribution` / `autoCompanionClean` 怎么处理？

- **推荐 C**：提升到全局 + 提示用户（安全，需一次写盘迁移）
- 若你嫌迁移风险高，也可以选 B'（保留字段但不显示，只读不再写）—— 我不推荐，会留技术债。

## 六、以及一条必须说的话

**TB-049（导出/后处理完全不可用）的修复应该先于本次重构。**

理由：本次重构会**大面积动 `PostprocessNodeOverride` 与消费端**。如果白名单 bug 还在，
重构完之后用户看到的仍是「导出位置不可用」—— **分不清是新重构引入的，还是老 bug 没修**。
先修 TB-049（方案 A + B 已就绪），让链路先通，再做重构，验证才有意义。

**顺序建议**：TB-049 修复 → 命名预览（TB-049 附带的小改动）→ 本次参数重构。
