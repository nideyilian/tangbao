# 0001 项目树统一为四个模块的共同上游，不另建第二棵树

- **日期**：2026-09-18
- **状态**：生效中
- **决策者**：杰哥（产品负责人）

## 背景

左栏素材库、SOP 分组、后处理、水印四个模块各自需要"产品线 → 产品 → 方向"这棵三级结构。
现状是同一棵树有**三份独立实现**（`AssetLibrarySidebar`、`sopGroupTree`、`postprocessProjectTree`），
外加一条 300ms 防抖的镜像链路 —— 这是漂移的高发区。

同时暴露了两个具体问题：

1. 参数是**全局单份**，物理上表达不了「月亮的图用 A 水印、网赚的图用 B 水印」，
   而这正是业务的实际形态。
2. 同一棵树三个实现，加一个字段要改三处。

关键事实：`collections` 表**本来就是唯一主源**（`AssetCollection`），SOP 分组早已通过 `collectionId`
单向投影、后处理早已通过 `selectedCollectionIds` 挂接 —— 所以这不是"要不要统一"的问题，
是**补完没补完**的问题。

## 决策

**统一到既有的 `collections` 这棵树，四模块共用；不新建第二棵树，也不引入"同步"概念。**

新增 `src/features/projectTree/`（参数层与表格投影），结构改动一律走 `useAssetLibraryStore` 的
collections CRUD，各模块通过订阅自动跟上。

## 理由

- 已有的投影方向是单向且正确的（collections → SOP / 后处理），反向再建一棵必然产生双主源。
- 参数层按 `collectionId` 存 `PostprocessNodeOverride`，逐级浅合并（方向 → 产品 → 产品线 → 全局默认），
  这是**唯一**能表达"每个方向不同参数"的位置。
- **没有同步按钮**：靠订阅 + 防抖（`sopGroupMirror`）驱动，避免"忘记点同步"这类静默失效。

**被否决的方案**：另建一棵"后处理树"并把参数挂上去。
否决原因：一棵树三个实现正是当前的病，再加一棵是把病制度化。

## 后果

- **正面**：新增字段只改一处；参数能按方向 / 产品 / 产品线逐级覆盖；UI 上"树上一切"都是同一份数据的投影。
- **代价 / 知情取舍**：`resolveImageOwnership` 需要**有界等待窗口**（2s / 250ms 步长），
  因为「任务完成→触发后处理」与「素材异步归档」是两条并发线，不等就会静默退回全局默认
  （表现为"树上参数没生效"）。这是统一带来的并发复杂度，**是必须付的成本**。
- **对后续代码的约束**：
  - 新增"结构"能力一律走 `collections` CRUD，不另建树、不新增同步入口。
  - SOP **刻意不加** `collectionId`：SOP 是**提示词资产**不是参数，提示词天然跨方向复用，
    单值归属会锁死；要做更细关联应加**多值标签**。
  - 新增工作区 / 新模块接树时，注意 `store.setAppMode` 兜底分支会改写非白名单值（见 `RISK.md` R-12）。
