## 零、一句话结论

后处理**主链路是通的** —— 18 个环节全都有实现，端到端能跑，相关 176 个测试全绿。
问题集中在水印这一段，有三类：

1. **没有护栏**：水印是整条链最复杂的一段（四维相乘），却是**唯一没有端到端断言**的一段；
2. **逻辑误耦合**：「不加水印 / 纯净版」也会走「贴标识符」的分支 —— **今天恰好看不出问题**，属于侥幸；
3. **查不出来**：没配水印时链路完全静默，用户没有任何线索，表现为「水印功能好像没做」。

**「先转图片再叠加」不推荐整包替换**：现有内存缓存已经消掉了同尺寸 / 同比例的重复渲染，而整条链真正的耗时在 **JPEG 编码 × 压缩二分**（与水印是参数还是图片无关）。详见第四节。

## 二、水印功能现状核查

### 2.1 贴水印逻辑：**已实现**，而且实现得完整

| 文件                                     | 职责                                                                                                  |
| ---------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| `composite/lib/compositeRendererV2.ts`   | `renderCompositeV2ToCanvas`（背景适配 + 叠 overlay）· `renderCombinedOverlay`（渲染 + 两级缓存）· `drawLayer`（唯一绘制入口：文字/图片、横排/竖排、描边/阴影/圆角/旋转） |
| `composite/lib/compositeIdentifier.ts`   | 标识符附加：有文字层 → 贴文案首尾；没有文字层 → 退化成一个左下角独立层                                |
| `composite/lib/compositeTextLayout.ts`   | 竖排逐字分列                                                                                          |
| `composite/lib/compositeRenderPlan.ts`   | `planBackgroundFit`（三种画面适配）· `mapLayerPositionToCanvas`（锚点 + 等比缩放）                    |

### 2.2 在哪个环节执行

落在**第 13 环节**，写盘之前：

```
writeVariant (taskPostprocess.ts:659)
  └─ renderVariant (:726)                      ← 这里决定用哪个预设
       ├─ preset 为 null → PLAIN_PRESET (1×1, 空图层)
       └─ renderCompositeV2ToJpegDataUrl (:739) 或 renderWithMaxKb (:741)
            └─ renderCompositeV2ToCanvas (compositeRendererV2.ts:385)
                 ├─ 背景按 fitMode 画进画布
                 └─ renderCombinedOverlay (:120) → renderOverlayAt (:186) → drawLayer (:264)
```

执行粒度：**每个产出单元一次**（渠道 × 尺寸 × 预设的笛卡尔积）。同一张源图会重复走很多次。

### 2.3 参数如何传递（六段接力）

```
① 项目树参数    params[方向].postprocess.watermarkPresetIds
                继承链：方向 → 产品 → 产品线 → 全局
② 逐级合并      applyPostprocessOverride → 白名单对象里的 watermarkPresetIds
                (postprocessMedia.ts:623；按渠道时 byMedia[mediaId] 优先)
③ 拆桶          bucketConfig.watermarkPresetIds
④ 展开单元      buildPostprocessOutputs → unit.watermark = { id, name }
                (postprocessMedia.ts:770；纯净版 / 未配预设时该字段不存在)
⑤ 取预设对象    resolveWatermarkPreset(unit.watermark.id) → bucketPresets
                (taskPostprocess.ts:631，在 useCompositeV2Store 全库扁平查找)
⑥ 传给渲染器    renderVariant 的 preset 参数
```

链路闭合，**没有断点**。第 ⑤ 步找不到预设时**整桶跳过**（`PP-PRESET-001`，`:420-423`）——
这是刻意的，不静默降级成无水印（否则等于交付了错误的投放素材）。

### 2.4 当前能否正常触发？

**能。但需要三步都做到，缺任一步就静默切成无水印。**

| 步骤                | 在哪做                                                                     | 缺了会怎样                            |
| ------------------- | -------------------------------------------------------------------------- | ------------------------------------- |
| ① 有一个水印预设    | 顶栏「水印预设」tab（`appMode='postprocess'`）                             | 库里没东西，第②步无从绑定             |
| ② 把预设绑到方向    | 中控台**左树选方向 → 右区「水印」tab 勾选**（`PresetManagementTab.tsx`，写 `setPostprocessOverride`） | 产出走 `PLAIN_PRESET`，**一声不吭**   |
| ③ 渠道勾上 + 方向开关开着 | 中控台「渠道与输出」tab                                              | 产出被跳过，并给提示                  |

证据：全局 `watermarkPresetIds` 默认是 `[]`（`storePostprocessMedia.ts:115`）——
**开箱状态就是「不加水印」**。

而**界面上的两条线索都不指向这件事**：

- 后处理弹窗里的「水印归属」是**只读**的（`paramSchema.ts:108-117`，`help: '只读。'`，
  `resettable: false`），只给一个「去中控台配水印」的跳转；

⇒ 这是最容易被误判成「水印功能没实现」的地方。

## 三、卡点清单（根因 → 方案 → 代价）

### 卡点 1｜水印链没有测试护栏（P0）

**现象**：`taskPostprocess.test.ts` 有 12 个用例，**没有一个覆盖水印**
（全文只有一处注释提到「水印」）。

**根因**：水印是「配置 → 桶 → 单元 → 预设 → 渲染」五段接力里唯一没有端到端断言的一段。
渲染器自己的 `compositeRendererV2.test.ts`（11 例）用**假 ctx** 验的是「画了几笔」，
验不到「这一笔是哪个预设来的」；`compositeIdentifier.test.ts`（22 例）验的是纯函数的叠加规则。

**为什么危险**：这条链最复杂（四维相乘），而它的失败方式**全是静默的** ——
叠错水印、叠不上、叠两份，界面都不会报。2026-09-22 那两次文字报障（R-83）
就发生在这段代码上，当时靠假 ctx 才验出来。

**方案**：在 `taskPostprocess.test.ts` 补三条断言。手法：用真的 `CompositeV2Preset` 对象，
把 canvas 渲染 stub 掉，只验「渲染被调用时拿到哪个预设」：

1. 方向 A 绑预设 X、方向 B 绑预设 Y → 两次渲染各收到自己的 preset；
2. `watermarkPresetIds: []` → 渲染收到 `null`（即走 PLAIN_PRESET）；
3. 预设 id 不存在 → 该桶 0 产出 + 一条 `PP-PRESET-001`。

**代价**：小。约 60 行测试，**不动生产代码**。当前性价比最高的一件。

---

### 卡点 2｜「不加水印」也会走「贴标识符」的分支（P0，今天是侥幸无害）

**现象**：所有「没挂水印预设」的产出（**包括纯净版**）都会走 `PLAIN_PRESET`，
而这个预设的基准画布是 **1×1**（`taskPostprocess.ts:65`）。标识符开启时，
渲染器会给它造一个左下角文字层：

- 字号 = `max(8, round(1 × 0.032)) = 8`（`compositeV2Types.ts:165` 的 `fontSizeRatio`）
- 再按 `min(1280/1, 720/1) = 720` 倍缩放（`compositeRenderPlan.ts:114`）

**实测**（真跑了一遍，不是推理）：

```
resolveIdentifierLayer(PLAIN_PRESET, {text:'★陈泽杰'})  →  返回图层（非 null）
rect @1280×720                                          →  {x:0, y:-7200, width:720, height:7920}
fontSize 实际                                            →  5760
```

框高 7920、y = −7200 ⇒ 文字中心落在画布**上方** 3240px。
**整段文字都在画布外，所以今天看不出来。**

**根因**：渲染器分不清这两件事 ——

- 「这个预设**就是没有水印**」（`PLAIN_PRESET` / `watermarkPresetIds: []` / 纯净版）→ 应该什么都不画；
- 「这个预设**有图但没文字层**」（纯图标水印）→ 才是 TB-041 说的「退化到左下角」。

代码里只有一个判据 `hasRenderableTextLayer(preset)`（`compositeIdentifier.ts:147`），
**两者都会命中**。`PLAIN_PRESET` 的注释写着「只借渲染链做尺寸适配与 JPEG 编码」，
说明作者没把「它也会被贴标识符」考虑进去。

**为什么是真卡点**：

1. 它是**巧合免疫**，不是设计 —— 保证「纯净版是干净原图」的居然是「基准画布恰好是 1×1」这个几何事实；
2. 哪天 `PLAIN_PRESET.baseCanvas` 改成真实尺寸（比如从示例底图取），**立刻**变成
   「每张干净的图都被糊上一行巨大文字」，而且是**所有方向、所有图**；
3. 纯净版语义上必须是「无水印原图」，现在它靠副作用成立。

**方案**（二选一，推荐 A）：

- **A（推荐）**：给渲染入口加显式开关，例如
  `CompositeV2RenderInput.applyIdentifier?: boolean`（缺省 `true`，既有行为不变），
  `PLAIN_PRESET` 那条路径传 `false`。语义直白，改动约 3 行，**不动任何既有产出**。
- **B**：让 `PLAIN_PRESET` 走一条不经过 overlay 的独立分支（直接适配 + 编码）。
  更干净，但要动 `renderVariant` 与渲染函数的签名。

**代价**：A 很小（渲染器 + `taskPostprocess` 各一处）。
**必须配反向验证**（把修复改回旧行为 ⇒ 新测试要变红），否则等于又加了一处没护栏的代码。

### 卡点 3｜「为什么这条产出没水印」查不出来（P1，可发现性）

**现象**：三种情况**全都静默** —— ① 没绑水印；② 绑了但被按渠道覆盖成空；③ 绑了空数组。
产出的就是干净原图，用户没有任何线索。

**根因**：「配置使然的空产出」只在一个文件都没出时才报 `PP-EMPTY-001`（`:555`）。
「出了图但没叠水印」不属于任何 issue 类别。

**方案**：在运行记录 / 结果弹窗（`postprocessRun.ts` / `PostprocessRunsDialog.tsx`）的
**结果摘要**加一行「本次产出：N 个文件，其中 M 个叠了水印」；M = 0 时补一句
「本次未叠任何水印（该方向未绑定预设）」。纯只读展示，不影响产出。

**代价**：小～中（要动 `PostprocessRun` 的记录结构 + 弹窗）。建议与卡点 4 同批做。

### 卡点 4｜渲染链全程传 base64，违反项目自己的性能基线（P1）

**现象**：`renderVariant` → `renderWithMaxKb` → `renderCompositeV2ToJpegDataUrl` → `blobToDataUrl`
**全程用 dataUrl**。每次压缩二分（最多 10 轮）都要：

- `blobToDataUrl` 一次（整张图转 base64 字符串）；
- `dataUrlSizeKb` 里 `split(',')[1]` 一次（**复制**整个 base64 字符串）。

1080×1920 的 JPEG 约 400KB → base64 约 533KB 的字符串，**每张图来回搬 10 次**。

**根因**：这条链从 A 套搬过来时就是 dataUrl 形态（`renderVariant.ts` 头注写明），
而 `architecture-constraints.md` 一章那条「整图字节优先：`saveImageBytes`，**新代码勿传 dataUrl**」
是针对后加的写盘路径定的。写盘侧已经做了补救
（`localSave.ts:425-438`：优先走 `saveCompositeImageBytes` + `decodeDataUrlToBytes`），
但**渲染中间态仍是 base64**。

**方案**：把 `renderWithMaxKb` 的中间产物从 dataUrl 换成 `Blob`
（`canvasToBlob` 本来就返回 Blob，只是被 `blobToDataUrl` 转掉了）；
`dataUrlSizeKb` 换成 `blob.size`（零成本）；最后写盘交给 `saveCompositeImageBytes`。

**代价**：中（动 `renderVariant.ts` + `compositeRendererV2` 的返回类型 + `writeVariant`）。
**注意**：`api.saveCompositeImageBytes` 是可选通道，**必须保留 dataUrl 兜底**。

### 卡点 5｜每轮压缩二分都从头重绘一遍（P1，性能）

**现象**：`renderWithMaxKb` 的每次迭代都调 `renderCompositeV2ToJpegDataUrl`，
而后者**每次都从 `renderCompositeV2ToCanvas` 开始** —— 背景适配 + overlay 叠加 +
`clearRect` 全部重做，只为了换一个 JPEG quality 参数。

10 轮迭代 = 10 次完整的背景绘制 + overlay drawImage；而其中只有 **JPEG 编码**是真正需要重做的
（overlay 本身有内存缓存，背景解码也有缓存，但 canvas 的绘制指令要重放）。

**补充事实（避免误判）**：overlay 的**重复渲染**其实已经被缓存消掉了 ——
`renderCombinedOverlay` 的缓存键是 `preset.id:updatedAt:WxH`（`compositeRendererV2.ts:111-118`），
**同尺寸跨渠道会命中**；同比例时还有 `base:` 键共享一份。所以实际渲染次数 = **去重后的尺寸数**
（约 10 个），不是「渠道 × 尺寸」。**这条不是「水印渲染太慢」，是「编码循环里混进了重绘」。**

**方案**：`renderWithMaxKb` 改成 —— 渲染**一次**到 canvas，然后对**同一张 canvas**
反复 `toBlob(quality)` 做二分。编码之外的部分不再重复。

**代价**：中，但**这是整条链最大的 CPU 开销所在**，收益最直接。
与卡点 4 高度耦合（都动 `renderVariant.ts`），**建议同批实施、一次验证**。

### 卡点 6｜配置包导入后的跨产品引用不校验（P2）

**现象**：`resolveWatermarkPreset` 在**全库扁平数组**里 `find(id)`（`:631-633`），
**不校验** `preset.productId` 与目标方向所属产品是否一致。

**根因**：水印库「按产品隔离」是靠**界面过滤**实现的，不是数据结构隔离
（`storeV2.ts:8-10` 写明这是刻意的取舍）。产出链因此拿不到「这个引用越界了」这个信息。

**后果**：导入配置包后，某个方向可能引用着**另一个产品库里的预设** —— 产出照叠不误，
但用户在水印 tab（按产品过滤后）**找不到它**，表现是「这个方向为什么会有这个水印」。

**方案**：产出前做一次**引用体检**（**不阻断产出**），把「引用了不属于本产品的水印」
记成一条 issue（建议新码 `PP-PRESET-002`），在卡点 3 那个摘要出口里提示。

**代价**：小。

## 四、「把参数化水印先转成图片再叠加」可行性评估

### 4.1 现有缓存已经做了多少

`renderCombinedOverlay` 有两级缓存，都在**内存**（`overlayCache`，LRU 384MB）：

| 情况                          | 行为                                                        |
| ----------------------------- | ----------------------------------------------------------- |
| 基准画布与目标**同比例**      | 渲染一份 `coverSize` 的大图，**所有同比例尺寸共用**（缩放绘制） |
| 比例不同                      | 按目标尺寸精确重绘，结果按 `preset.id:updatedAt:WxH` 缓存    |
| 同尺寸跨渠道 / 跨图片         | **命中缓存**（键里只有尺寸，没有图）                         |
| 改了标识符 / Logo             | 缓存键含 `identifierSignature` / `logoSignature` → 自动失效（R-32） |

⇒ 「同一批次内不重复渲染」**已经做到了**。预转图片能多拿到的只有「跨批次 / 跨重启」的复用。

### 4.2 三个关键环节的现实约束

**① 参数 → 图片的渲染**

现在必须是**渲染进程主线程**的 canvas（`document.createElement('canvas')`）。
要挪到离屏 / 主进程得换 `OffscreenCanvas` 或 `node-canvas` —— 后者在本机是原生模块
（Electron 要 rebuild），**而且字体环境会变**：现在用的是 canvas 的 `sans-serif`，
主进程侧拿到的字形未必一致 ⇒ **水印字体会变**。这是最容易低估的坑。

**② 图片生成（转什么格式）**

overlay 是**带透明通道**的，无损就只能 PNG：1080×1920 的透明 PNG 通常 **1–3MB**，
而它的内容只是几个文字 + 一张 logo。存 10 个尺寸 × N 个预设 = 几十 MB 缓存，还要做 GC。

**③ 叠加位置与方式（最硬的难点）**

现在的叠加**不是「缩放一张图贴上去」**，而是**按目标尺寸重新算每个图层的位置**：
`mapLayerPositionToCanvas` 用 `scale = min(target.w / base.w, target.h / base.h)` 等比缩放，
锚点与边距都跟着变。这保证了「同一套水印在竖版和横版上看起来一样大」。

若预转成一张基准图再缩放贴上去：基准 1080×1920 贴到 1280×720 时**必须非等比拉伸**
（否则盖不满），水印会被**横向拉开**。要保持观感，就只能**按尺寸各转一张** ——
那「预转」就退化成「把内存缓存搬到磁盘」，复杂度上升、收益只剩跨会话。

### 4.3 结论

**不推荐整包替换。** 四条理由：

1. 同批次内的重复渲染**已经被内存缓存消掉了**，预转图片省不掉「每个尺寸第一次渲染」；
2. 整条链真正的耗时在 **JPEG 编码 × 压缩二分**（卡点 5），**与水印是参数还是图片无关**；
3. 引入的代价不小：透明 PNG 体积、字体环境差异、缓存失效与 GC、离屏 / 主进程能力；
4. 一旦预转，「改水印」从**即时生效**变成「要等重建」——
   与 TB-041 验收标准 4（改文本后产出**立即**变化）直接冲突。

**如果确实要做，按这个顺序（更划算的替代）**：

- **甲（优先）**：卡点 5 —— 渲染一轮 + 多次 `toBlob(quality)`。**这是直接的性能收益。**
- **乙**：卡点 4 —— 中间产物去 base64，用 Blob / 字节。省掉每张图 10 次 base64 往返。
- **丙（可选）**：若将来确实需要跨批次复用，做**磁盘缓存**而不是「转换水印」——
  键 = `预设 id + updatedAt + logo 签名 + 标识符签名 + 尺寸`，存透明 PNG，
  落 `userData/cache/watermark-overlay/`，按容量 LRU + 版本号失效。**不动渲染语义**，风险可控。

### 追加落地（2026-09-23 第二轮）：杰哥的真实需求是「后处理太慢」

杰哥原话：「**我是觉得当前后处理太慢了**」。前面几轮我都在猜他关心什么，这一句才是需求本身。
据此做了实测诊断与优化，见 **`BACKLOG` TB-114**。要点：

- **实测**（从本机库 529 条产出记录的时间戳反推）：单变体 **168ms ~ 1312ms（8 倍）**，
  而渠道构成 / 目标尺寸 / 源图数量完全一致。
- **根因**：**JPEG 编码轮数**。慢的那批每变体走满 **10 轮**（0.9 + 探底 + 8 轮二分），
  快的只走 1 轮。联立解出单轮编码 ≈ **127ms**、其他开销 ≈ 41ms。
- **已做**：二分 8 轮 → **两点对数插值**（典型 3 次编码）；空覆盖层不再合成；
  目录链 IPC 缓存；新增耗时埋点（`paintMs / encodeMs / encodeCount / writeMs`，显示在进度面板）。
- **预期**：慢变体 1312ms → 约 400ms（**未经真机计时确认**）。

### 出向 base64 的最终判断（2026-09-23，实测后推翻我自己的估算）

我先前说它「该做但不紧急，1000 张省 10-25 秒」—— **错了，那个估算按「自写 JS 循环」算的**。
实际这条链走的是**原生实现**（`Uint8Array.prototype.toBase64` / `fromBase64`，本仓 Electron 43 =
Chromium 133+ 确实支持），本机实测（400KB 图）：

| 步骤                   | 实测       |
| ---------------------- | ---------- |
| 编码成 546KB 字符串    | 0.35 ms    |
| 解码回字节             | 0.24 ms    |
| **一次往返**           | **0.59 ms** |
| 1000 张产出的活，合计  | **0.59 秒** |

对照：同尺寸的 **JPEG 编码本身是 50–150ms**（实测反推单轮 ≈127ms）——
base64 只占它的 **1/100 ~ 1/250**。而且 TB-113 已经把往返从「每轮一次」降到「每产出一次」。

⇒ **结论：不做。** 改动要碰三个出口 + 两条写盘通道（`saveCompositeImageBytes?` 是可选通道，
回退路径不能删，`ipc-handlers.test.ts:908` 专门守着），**拿风险换 0.59 秒，不划算。**
