# 糖包 项目管理升级方案

> 角色：高级项目经理（PM）视角，非代码审计视角。
> 基线：`0.1.1` / `c3928db` / 2026-09-18。
> 方法：全部结论来自实测（git 历史、门禁配置、docs 结构、测试结构、事故记录），附证据位置。

---

## 结论先行

**这个项目的工程纪律是上游水平，项目管理水平是创业早期的随性水平。两者严重不匹配。**

三个判断：

1. **不缺执行力，缺"需求的生命周期"。** 需求 100% 从对话来、做完只写进日志，没有编号、没有状态、没有验收标准。
   代价已经出现：工作单元编号已经失控，方案文档出现"已过期"的自我修正。
2. **最大的隐性资产正在裸奔。** `.gitignore:29-30` 把 `.workbuddy/` 排除在版本控制外，
   而项目全部硬结论（约 27 条数据安全级陷阱、决策记录、操作配方）就存在那里。`MEMORY.md` 一天内
   因超限被压缩 **4 次**（22830 → 17825 → 24400 → 17900 → 16745 → **10069** 字节）——
   这是"用错载体"的明确信号，不是勤奋。
3. **这个项目的"团队"是 1 个人 + N 个无状态 AI 会话，但没有任何针对这个形态的管理机制。**
   近 24 小时 **3 次「无法生图」级事故，全部由并行会话引起**（见 C-1）。当前唯一的防线是
   `MEMORY.md` 里的一句口头约定。

**最紧急的一件事（本周做，成本 2 小时）**：建立 `ROADMAP / BACKLOG / RISK / ADR` 四个文件并挂进 `AGENTS.md`。
理由是它同时解掉问题 1、2、3 的根——**把"只存在于对话和记忆里的项目管理"变成"存在文件里、AI 会话自动加载的项目管理"**。

## 二、问题清单（按优先级；每条含证据 / 后果 / 修复成本）

### P1 —— 必须解决，否则积累下去会反噬

#### P1-1 需求没有生命周期：无编号、无状态、无验收标准

**证据**

- `tasks/` 目录的 9 个 json 是**应用生成的图片任务记录**（含 `prompt` / `inputImageIds` / `outputImages`），
  与项目管理无关 —— 即全仓**没有任何 backlog 载体**。
- 工作日志里同时存在**三套互不兼容的轮次编号**：
  `2026-09-18.md` 里既有「第一轮 / 第二轮 / 第三轮 / 第四轮 / 第五轮」（水印专题内部编号），
  又有「第十九轮 / 第二十轮 / 第二十一轮」（修复专题编号）。**同一份文件里两套编号并行** →
  无法回答"第十八轮是什么、做完没有"。
- 需求原文只存在于对话里。日志里的"杰哥原话"是**追记**，不是事前规格。
- `docs/superpowers/plans/` 是规格驱动开发的正确姿势（一案一文件、按日期），但**最后一次是 2026-08-20**，
  rebrand 成糖包后彻底断档。

**后果**：无法回答"这个需求做了吗 / 排在哪 / 什么时候能验收"。看似省事，实际是把账记在脑子里，
而脑子已经被 27 条陷阱 + 2535 个用例 + 47 份文档占满了。

**修复成本**：低（建 `docs/BACKLOG.md`，把在途事项回填，之后每个需求开工前加一行）。

#### P1-2 知识资产不入库 + 载体错配

**证据**

- `.gitignore:29-30`：`.workbuddy-ai/`、`.workbuddy/` → 记忆文件**永不进库**。
  项目全部硬结论（`MEMORY.md` 15 节 + 2 天日志约 1100 行）**只存在于这一台机器**。
- `MEMORY.md` 一天内被压缩 4 次：`22830 → 17825`（10:17 前后）→ `24400 → 17900`（下午）→
  `16745 → 10069`（晚间）。每次压缩都丢掉过程细节、只留结论 —— 反复发生说明**量级超过了载体设计容量**。
- 与之对照：`docs/tangbao-ops-runbook.md` 在库里、277 行、结构清晰 —— 这才是知识该待的地方。

**后果**：① 换机器 / 磁盘故障 = 全部沉淀归零；② 无法回溯"某个结论是什么时候、因为什么改的"；
③ 每次会话都要重新"注入 + 截断"，注入被截断的部分对 AI 就等于不存在。

**修复成本**：低（给 `.workbuddy/` 开一个白名单：只把 `memory/MEMORY.md` 与 `memory/*.md` 入库；
或用 `git add -f`）。真正要改的是**分层**：

| 层     | 载体                          | 容量       | 内容                          |
| ------ | ----------------------------- | ---------- | ----------------------------- |
| 索引层 | `.workbuddy/memory/MEMORY.md` | ≤ 10KB     | **只放指针 + 铁律**，不放配方 |
| 配方层 | `docs/tangbao-ops-runbook.md` | 无上限     | 可执行操作步骤                |
| 方案层 | `docs/*.md`                   | 无上限     | 需求 / 设计与实施             |
| 决策层 | `docs/adr/*.md`               | 一案一文件 | 为什么这么定                  |
| 风险层 | `docs/RISK.md`                | 表格       | 带分级的风险与缓解            |

#### P1-3 缺单一真相源：同一事实写多处，必然漂移

**证据（已发生的漂移，非推测）**

- 日志原文：「`MEMORY.md` 写『推 GitHub 命令见 runbook 二』，但 **runbook 第二节的正文是
  `createDesktopJsonStorage`，根本没有推送章节** —— 指针是从旧编号里带过来的。」
- `docs/postprocess-unify-on-hanling-plan.md:271` 的「下一批（未做）」，**当天就被做完了**，
  日志自己补了一句「该行已过期」。
- 同一条 `canvas.toDataURL → canvasToWebpDataUrl` 的修复方案，在
  `docs/project-health-audit.md` 里**重复写了两遍**（第 95-101 行与第 112-118 行）。

**后果**：文档越多越不敢信，最后等于没有文档。这是"文档熵"的典型路径。

**修复成本**：低（确立"每个事实只有一个家"，其它地方只放指针）。

#### P1-4 文档没有生命周期：豆泡时代的遗产与糖包的现状混在一个目录

**证据**

- 明确写着旧基线的：`docs/performance-diagnosis.md`、`docs/optimization-plan.md`、
  `docs/project-health-audit.md`（标题下写「版本基线：`v0.8.19`（`edc7db4`）」）、
  `docs/analysis-doupao-liangnianban.md`、`docs/revert-generation-0.7.56-asset-library.md`。
- `PRODUCT.md` 通篇是**素材库 M1–M20 的落地清单**，且 `:49` `:66` 指向 `docs/superpowers/specs/*`、
  `docs/superpowers/plans/*` 的具体文件 —— 这些是**迁入前项目**的设计，与糖包当前主线（后处理 / 水印 / SOP）已脱节。
- `CODE_WIKI.md`（1035 行）与 `README.md`（475 行）同为豆泡时期产物。
- 糖包 rebrand 后**没有任何一份"哪些文档现行有效"的清单**。

**后果**：新会话（人或 AI）读到的第一手资料可能是错的。本次诊断就先用了一份
v0.8.19 基线的体检报告做参照，确认后才排除。

**修复成本**：低（在 `docs/README.md` 建索引，给每份文档标 `现行 / 参考 / 归档`）。

#### P1-5 没有版本目标：只有 changelog，没有 roadmap

**证据**

- `RELEASE.md` 结构 = 纯 changelog（v0.1.1 → 分界线 → v0.8.20 …）。
- 24 个提交里只有 1 个 `release:` 提交，`package.json` 停在 `0.1.1`。
- 最新在途工作（后处理统一到瀚灵 / 水印归属统一树 / 按渠道覆盖）是**功能级大地震**，
  但没有任何文件说明"0.2.0 要交付什么、什么时候算完"。

**后果**：优先级只能靠"当下最急"决定，无法判断"这件事该不该现在做"。
本次诊断中 `docs/postprocess-unify-on-hanling-plan.md` 的"待拍板"状态就是典型 ——
**方案写完了，但它排在哪个版本、什么条件下开工，无处可查**。

**修复成本**：低（建 `docs/ROADMAP.md`，写清当前里程碑的交付物与完成判据）。

### P2 —— 该修，属于机制缺陷

#### P2-1 门禁的形状不对：只能证伪"代码坏了"，不能证伪"声称改了但没落地"

**证据**

- `tsconfig.json:19-20`：`"noUnusedLocals": false`、`"noUnusedParameters": false`
- `eslint.config.js:48`：`'@typescript-eslint/no-unused-vars': ['warn', ...]`（不是 error）
- 后果实证（`docs/project-health-audit.md` P1-1）：一个**只加了 import、没换调用点**的性能修复
  （`src/lib/db.ts:31` 的死 import 是化石），在 `verify` 全绿（235 文件 / 2247 用例）的状态下，
  被写进 `RELEASE.md` 当成"已完成"发布 —— **19 个图片入库调用点全都没改**。

**后果**：门禁给了虚假的安全感。绿灯不代表做完了，只代表没写坏。

**修复成本**：极低（两处配置：`warn → error` 需先清存量；建议先对 `src/**` 开 error，
存量 113 处告警分批清）。

#### P2-2 无覆盖率度量，测试金字塔畸形

**证据**

- `package.json:21` 只有 `vitest run`，无 `coverage`；`vite.config.ts` 无 coverage 配置。
- 用例集中在**纯函数层**（`lib/*.test.ts` 约 150 个文件），而最危险的**协调层**明确无覆盖：
  - 日志原文：「`store.ts` 那份改动**没有单测覆盖**（在 `executeTask` 闭包内，要 mock 整条生图链）」
  - 日志原文：「⚠️ **`InputBar.tsx` 没有测试文件**，标志复位那段（4 处）无单测覆盖」
- 这两个文件恰好是最大的两个（`store.ts` 13346 行、`InputBar.tsx` 5565 行）。
- 近 24 小时 **3 个线上级 bug 全部出现在这两处**：任务数量回退、看门狗孤儿结果、比例提示词不生效。

**后果**：2535 个用例是很高的数字，但它测的恰好不是最容易出事的地方。**测试覆盖了"能测的"，不是"危险的"。**

**修复成本**：中（先加 `coverage` 报告看数，不设硬门槛；再给 `InputBar` 建第一个测试文件，
把 3 次事故各落一条回归用例）。

#### P2-3 提交粒度不可回滚

**证据**：`8b26160 refactor(后处理)` = **54 文件 / +338 −8978 行**；`5e0b685` = 23 文件 / +2604 −464。

**后果**：出问题时无法单项回滚，只能整块 revert（而整块 revert 会连带把已验收的改动一起撤掉）；
`git bisect` 在这种粒度下形同虚设。

**修复成本**：零成本（只改习惯：按"可独立验收的最小单元"提交，A 套退役那种大重构按
「删消费方 → 剥字段 → 清死代码」分 3 次提交，日志里其实已经记录了正确的顺序）。

#### P2-4 并行会话没有排他协议 —— 这是本项目的真实"团队管理"问题

**证据（24 小时内 3 次事故，全部由并行引起）**

| 时间  | 事故                                                 | 根因（日志原文）                                                                               |
| ----- | ---------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| 00:46 | 报"无法生图，卡在提示词生成阶段"                     | 「第四节那批改动经 **HMR 整页刷新打断了运行中的窗口**」                                        |
| 下午  | 窗口 `chrome-error://chromewebdata/`，点什么都没反应 | 「**另一个 WorkBuddy 会话在同一个仓库反复 `npm run dev`**」，41731 `strictPort` + 单实例锁互抢 |
| 11:05 | 3 条快照记录被写坏引发渲染崩溃                       | 写库时**没带 `record_id` 条件**，`WHERE namespace=...` 一把梭，覆盖了 3 条记录                 |

**物理约束（这是管理机制必须尊重的现实）**

- `vite` 固定端口 `127.0.0.1:41731`（`strictPort`）
- Electron 单实例锁按 `userData` 独占
- localStorage leveldb **被应用进程独占 `LOCK`**
- HMR 会把任何一条工作线的改动**热更新进另一条正在使用的窗口**

**后果**：并行不仅不加速，还会**互相制造故障**，且故障表现为"功能不工作"，极难归因。

**修复成本**：低（成文协议 + 端口约定表；重度并行时用 `git worktree` 物理隔离）。

#### P2-5 风险只有叙述，没有登记

**证据**：`MEMORY.md` 的「陷阱（数据安全级）」节约 27 条，全部是**叙述式**：
「禁用 `git rm`（曾让 `src/` 576 文件消失）」「Bash 工具会吃 `\\`、`${}`」…
没有分级、没有触发条件、没有检测手段、没有缓解责任人。

**后果**：新会话必须通读全部 27 条才知道哪条与当前任务相关；且没有"这条风险是否已消除"的状态。

**修复成本**：低（转成 `docs/RISK.md` 表格：ID / 等级 / 触发条件 / 检测 / 缓解 / 状态）。

## 三、方案：三层单一真相源 + 两个清单

### 3.1 架构

```
┌─ Layer A  决策层（回答"做什么、什么时候算完"）────────────────┐
│  docs/ROADMAP.md        ← 唯一目标源：当前里程碑 + 完成判据     │
└──────────────────────────────────────────────────────────────┘
                ↓ 拆
┌─ Layer B  工作层（回答"现在在做什么、卡在哪"）────────────────┐
│  docs/BACKLOG.md        ← 唯一需求池：TB-### 编号 + 状态 + 验收 │
│  docs/adr/NNNN-*.md     ← 唯一决策记录：一条决策一个文件        │
└──────────────────────────────────────────────────────────────┘
                ↓ 约束
┌─ Layer C  风险/知识层（回答"哪些坑不能踩、配方在哪"）──────────┐
│  docs/RISK.md                 ← 唯一风险登记册（R-### 分级）   │
│  docs/tangbao-ops-runbook.md  ← 唯一操作配方                   │
│  .workbuddy/memory/MEMORY.md  ← 索引（≤10KB，只放指针 + 铁律） │
└──────────────────────────────────────────────────────────────┘
```

**单一真相源规则（一句话版本）**：一个事实只允许有一个家，其它地方只能是**指针**（`见 docs/RISK.md R-07`），
不允许复述内容。这一条直接解掉 P1-3 的全部实证漂移。

### 3.2 工作单元：TB-### 的定义（把"轮次"变成有生命周期的对象）

现在的"第 N 轮"是一个**序号**，不是一个**对象** —— 没有状态、没有验收、做完就沉进日志。

替换成：

```markdown
### TB-014 后处理按图片归属自动匹配参数

- **来源**：杰哥原话「默认自动采用图片所在方向文件夹对应的参数，无需手动选择」（2026-09-18）
- **状态**：DONE（commit `5e0b685`）
- **验收标准**（可测，不是形容词）：
  1. 勾选范围外的方向完全不产出
  2. 有归属 → 产出到归属方向目录；无归属 → 退回全局勾选
  3. `npm run verify` 全绿
- **影响面**：`store.ts` / `taskPostprocess.ts` / `features/projectTree/*`
- **回滚点**：`git revert 5e0b685`
```

**状态只有 5 个**（不要更多）：`TODO / DOING / BLOCKED / DONE / DROPPED`。
`BLOCKED` 必须写明"等谁 / 等什么"。

**WIP 限制 ≤ 2**：这个项目的团队是 1 人 + N 个 AI 会话，但**写线只能有一条**（P2-4 的物理约束）。
在 `BACKLOG.md` 顶部维护一个"在途"表格，超过 2 条就说明在并行，要显式承认并分配隔离手段。

### 3.3 两个清单：开工 / 收工（DoR / DoD）

这是把"纪律"从记忆搬到文件的最短路径，也是唯一能约束 AI 会话的抓手（AI 每次都会读 `AGENTS.md`）。

**开工清单（Definition of Ready）** —— 满足才允许动代码：

- [ ] `BACKLOG.md` 里有这个 TB 编号，验收标准写得能测
- [ ] **确认当前没有别的写线在跑**：查 `dev` 是否在跑（`netstat` 查 41731）、确认另一会话在改哪些文件
- [ ] 影响面清单已列出（要动哪些文件）；若与在途线重叠 → **停下来，先解决冲突**
- [ ] 已读 `RISK.md` 中与本任务相关的风险项
- [ ] 若涉及持久化 / 数据库 → 先确认备份（`backup-before-*`）

**收工清单（Definition of Done）** —— 任一条不满足即不算完成：

- [ ] `npm run verify` 全绿（含渲染 + 主进程双端类型检查）
- [ ] `npx prettier --write` 已跑（`AGENTS.md` 的硬要求）
- [ ] `BACKLOG.md` 状态更新为 `DONE`，并把**验收证据**（测试数 / commit / 实测数字）写进该条
- [ ] 若有架构级决策 → 补一条 `docs/adr/`
- [ ] 若踩到新的坑 → 登记 `RISK.md`，并把操作配方写进 `runbook`
- [ ] **提交并推送**（不留未提交改动过夜）；提交信息用 Conventional Commits 简体中文
- [ ] 若对外可见 → 更新 `RELEASE.md`

### 3.5 团队管理：这个项目的"团队"是 1 人 + N 个 AI 会话

不套 Scrum（每日站会 / 故事点 / 速度图对这种形态是荒谬的）。要建的是**三条针对"无状态执行者"的协议**：

**协议一：单写线原则（资源排他）**

> 同一仓库同一时刻**只允许一条写线**。需要真并行时，用 `git worktree` 物理隔离，
> 并遵守端口 / userData 约定，防止 HMR 互相污染。

| 会话   | worktree 路径              | vite 端口     | userData                      |
| ------ | -------------------------- | ------------- | ----------------------------- |
| 主写线 | `D:\AAA\TANGBAO`           | 41731（默认） | `%APPDATA%\tangbao`           |
| 并行线 | `D:\AAA\TANGBAO.wt-<主题>` | 41800+        | `%APPDATA%\tangbao-wt-<主题>` |

**协议二：会话交接三件套（对抗无记忆）**

AI 会话没有记忆，所以"交接"必须靠文件。每次开工 / 收工各读 / 写三处：

- 开工：`AGENTS.md`（规范）→ `BACKLOG.md`（现状）→ `RISK.md`（相关风险）
- 收工：`BACKLOG.md`（状态 + 证据）→ 当日 `memory/YYYY-MM-DD.md`（只记**过程与判断依据**，
  硬结论一律外迁到 `RISK.md` / `runbook` / `adr`）

**协议三：角色边界（防止 AI 越权改范围）**

| 角色       | 谁      | 职责                                        | 禁止                                                     |
| ---------- | ------- | ------------------------------------------- | -------------------------------------------------------- |
| 产品负责人 | 杰哥    | **唯一决策者**：拍板范围、验收、版本        | —                                                        |
| 执行       | AI 会话 | 实现 TB、写测试、记录证据、跑验证           | 不擅自扩大范围、不擅自改 `AGENTS.md`、不替用户改全局配置 |
| 记录       | AI 会话 | 维护 `BACKLOG` / `RISK` / `runbook` / `adr` | 不改写历史结论（只追加与标注过期）                       |

> 这条协议有现成的正面案例可以照抄：日志里「杰哥四项拍板：手动入口保留 · 多水印需要 · 分发保留移植 · 不自动归档」
> —— **AI 只提问、不代替决策，杰哥拍板、AI 落地**。这个模式跑得很顺，把它固化成规则即可。
> 反面案例也已出现：「不替用户改全局启用范围」（`selectedMediaIds` / `selectedCollectionIds` 留给杰哥定）—— 这是对的。
