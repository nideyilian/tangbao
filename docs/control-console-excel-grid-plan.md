## 零、复述：我理解的前提

杰哥原话：「所有数据都是中控台的投影，中控台拥有全部数据，要认清中控台的重要性。」

我理解为三条，且这三条是本次需求的地基（不是修辞）：

1. **中控台是数据的本体，不是众多页面里的一个。** 它持有全量数据的所有权：方向（项目树）、渠道与尺寸、输出位置、水印归属、分发、命名。生成工作区、素材库、后处理弹窗、SOP、Agent 都是**同一份数据在不同视角下的投影**——它们可以读、可以发起修改，但**不允许持有第二个真相源**。
2. **所以「表格化」不是给中控台换个好看的列表，而是给这份数据本体建一个统一的可编辑读写口。** 表格是视图，导入导出是这个读写口的批量形态；两者必须落在同一套字段定义上，不能各写一份。
3. **任何投影页上的改动都必须回到中控台那份数据。** 否则就会重演仓库里已经记录过的病——`src/features/postprocess/paramSchema.ts:10-17` 写着「同一个参数两个入口：一处改了、另一处显示不一致」；`MediaSection.tsx:36` 记着「改掉了原字段说明的自相矛盾」。

这条定位在代码里**已经写下来了**，不是我替你安的：

| 出处                               | 原话                                                                                     |
| ---------------------------------- | ---------------------------------------------------------------------------------------- |
| `lib/controlConsoleSections.ts:13` | 「**中控台是全部参数的统一编辑入口**……不设『中控台只能改全局、节点级要去项目树』的断层」 |
| `lib/controlConsoleSections.ts:17` | 「给了作用域却什么都不变，比不给更糟」                                                   |
| `docs/BACKLOG.md` TB-053 第三轮    | 你的原话：「有没有可能那个所谓的铁律是你理解错了呢，我说只有一个入口就是指中控台」       |

**而这条定位当前只成立了一部分。** 见下节——这是本次需求真正的难点所在。

### 1.1 四个缺口（都影响「完整导入导出」的可行性）

**缺口 1 —— 节点级只覆盖 4 个字段，两个分区是纯全局的。**
`PostprocessNodeOverride`（ADR-0011 收窄后）只有 `enabled` / `outputDir` / `watermarkPresetIds` / `byMedia`。
所以「渠道与尺寸」（`MediaSection.tsx:24-31`）和「分发」（`DistributionSection.tsx:6-14`）**不消费作用域**：
选中某个方向时，这两块改了是对全局生效的。→ 表格里如果按「方向 × 渠道」铺开，就会出现**看起来能按方向配、实际改的是全局**的假象。这是必须先裁决的事（§七.5）。

**缺口 2 —— 全局水印清单在前端没有写入点。**
`CompositeWorkspace.tsx:39-40`：「全局清单在前端没有写入点，各方向自己声明才是权威」。
即：`watermarkPresetIds`（全局基线）是中控台**只读**的。→ 「中控台拥有全部数据」在水印全局层不成立。

**缺口 3 —— 素材（`GeneratedAsset`）与任务（`TaskRecord`）根本不在中控台。**
它们各自有 store 与界面。中控台只能通过"方向归属"间接引用。
→ 若"完整导入导出"指中控台口径，则这两块**不在范围内**；若要做全量，就必须先承认中控台要新增这两个数据面的入口（属于范围扩张，需你拍板）。

**缺口 4 —— 预设图层是嵌套树，不能扁平化。**
`CompositeV2Preset.layers[]` 是 `image`/`logo`/`text` 三型联合，带 `position`（anchor 或 free 两套形状）、`shadow`、`stroke`。
→ 硬塞进一行会有 30+ 列且语义冲突。方案是**拆主子表**（§二.9），画布编辑保留。

## 三、表格组件形态（设计系统侧）

现有 `Table*`（`data-display.tsx:210-240`）是**样式基元**，缺能力。建议新增一个 `DataGrid`，而不是改 `Table`（`Table` 已被别处消费，改它会牵连）。

| 能力       | 要求                                                                   | 理由                                                        |
| ---------- | ---------------------------------------------------------------------- | ----------------------------------------------------------- |
| 单元格编辑 | 文本 / 数字 / 开关 / 枚举下拉 / 路径（带选目录）/ 标签列表（逗号分隔） | 六种编辑器覆盖 §二 全部列                                   |
| 草稿态提交 | 失焦或回车提交，`Esc` 撤回                                             | `MediaTableManager.tsx:210-252` 的 `SizeField` 已踩过这个坑 |

| 列冻结     | 首列（主键/名称）冻结                                                  | 宽表横向滚动时的可用性下限                                  |

## 四、导入导出设计

### 4.1 范围（中控台口径）

导出物 = **一个工作簿**，每张 Sheet 对应 §二 的一个区域，Sheet 名用**稳定英文 id**（不随 UI 语言变）：

```
中控台数据.<xlsx>
├─ directions          ① 方向表
├─ channels            ② 渠道表
├─ channel_sizes       ③ 尺寸表（外键 mediaId）
├─ node_params         ④ 方向级参数
├─ output_dirs_global  ⑤ 全局输出位置
├─ output_dirs_node    ⑥ 方向 × 渠道 覆盖
├─ watermark_binding   ⑦ 方向 × 预设 归属
├─ presets             ⑧ 水印预设
├─ preset_layers       ⑨ 水印图层（外键 presetId）
├─ distribution        ⑩ 分发配置
├─ naming              ⑪ 命名与署名
└─ output_manifest     ⑫ 产出清单（只读，导出有、导入忽略）
```

**导出**：全部 12 张表，默认全选，可勾掉某张（勾掉 = 该区域完全不进包，导入时不动它）。
**导入**：按表独立判定，允许「只导渠道与尺寸」这种部分导入；**表不在包里的区域一律不动**（比 TB-042 的槽位口径更细）。

### 4.2 字段映射机制（这是「映射清晰」的关键）

| 规则                               | 做法                                                                                                                         |
| ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| 匹配一律按**字段键**，不按中文表头 | 表头行写成 `字段键` + 下一行 `中文显示名`（双行表头），或首行 `渠道ID (id)` 形式；解析只取 `(…)` 里的键                      |
| 导入方表头容错                     | 复用 `agentBatchImport.ts:5-23` 的别名机制（`HEADER_ALIASES`），但**只作为兼容垫**，导出永远用规范表头                       |
| 主键列受保护                       | 导入时若某行的主键与库中不同（被改过），**整行拒绝并报行号**，不静默当新行插入                                               |
| 未知列                             | 报「第 N 列未知，将忽略」并列出列名（不静默丢弃——静默失效是本仓已知病灶，见 `architecture-constraints.md` 七·五章）          |
| 列顺序                             | 导出固定顺序；导入按表头匹配，顺序无关                                                                                       |
| 空值语义                           | **空字符串 ≠ 未设置**。目录类字段空 = 继承（继承是语义，不是"没填"）；必须与「显式覆盖为空」区分，表格里用「继承」复选框表达 |

### 4.3 数据一致性要求（六条硬约束）

**1. ⚠️ `sizeId` 是由宽高派生的——这是本方案最大的技术陷阱。**
`buildPostprocessMediaSizeId(mediaId, width, height)`（`storePostprocessMedia.ts:228`）。
在表格里把某行 `1280×720` 改成 `1280×800`，**主键会跟着变**：

- 若导入按「改」处理 → 旧 id 消失、新 id 出现，任何指向旧 id 的引用（产出计划、⑥ 的覆盖、历史产出记录）**静默失联**；
- `updateMediaSize` 里已有重算逻辑与「同宽高撞车则放弃修改」的保护（`storePostprocessMedia.ts:318-323`），导入器必须复用它，**不能绕过 action 直接改数组**。

→ 要求：尺寸表导入时，宽/高变化的行按「删旧 + 增新」显式处理，并在 dry-run 里预告
「将重命名 3 个尺寸、影响 2 个方向的产出计划」。绝不静默。

**2. 主键不可变。** `id` / `parentId` / `mediaId` / `presetId` / `collectionId` 在所有表里都是引用目标。改主键 = 断链。

**3. 写入必须走 store action，禁止直接写 SQLite。**
落盘是 `local-saves/db/asset-kernel.sqlite` 的 `app_data_records`（手工写库三铁律：编码按 namespace、带 `record_id` 条件、停应用 + 备份 + 改完全库体检 —— `RISK.md` R-04/R-05）。
导入必须调 `usePostprocessMediaStore` / `useProjectTreeParamsStore` / `useAssetLibraryStore` / `useCompositeV2Store` 的既有 action，让 zustand 自己落盘。

**4. 引用完整性，悬空即拒绝。**
外键指向不存在的行（如尺寸表里的 `mediaId` 找不到）→ **拒绝整表并列出缺失键**，不做"猜一个补上"。
但要注意一条既有语义：`mediaOutputDirs` 的键**允许指向已删除的渠道**（`storePostprocessMedia.ts:100` 刻意不剪枝），所以这条校验只对 ③⑥⑦⑨ 生效，⑤ 豁免。

**5. 跨机必然失效的字段，导入时必须显式报警而不是静默留空。**
`sampleBackgroundPath`（⑧）、图层的 `asset.kind='path'/'internal'` 路径（⑨）、`targetDir`（⑩）、所有输出目录（⑤⑥）—— 换台机器这些路径都不存在。

**6. 三模式 + 预演 + 回滚（沿用 TB-042 已定案的机制，不新造）。**
合并（默认，按主键去重追加）/ 覆盖（整体替换所选表）/ 仅配置。
导入前 dry-run 必须展示：将新增 N 行、覆盖 M 行、跳过 K 行、拒绝 J 行（带原因）。
导入中途异常 → 回滚到导入前状态（TB-042 §2.3#2 的教训：当时的失败会留下半吊子状态，比导入前更糟）。

### 4.4 文件格式：.xlsx 还是 .csv

| 方案                | 优点                                    | 代价                                                                                                                        |
| ------------------- | --------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| **.xlsx（建议）**   | 多 Sheet、类型保留、用户真正要的"Excel" | **本仓无 xlsx 依赖**（已核实：`src`/`scripts`/`electron` 内只有 CSV 相关代码）。需引 `sheetjs`（xlsx）或用最小 OpenXML 写出 |
| .csv（单表/多文件） | 零依赖，已有 `agentBatchImport.ts` 先例 | 一个区域一个文件（12 个文件）或压平为一张长表；中文表头在 Excel 里会被自动转日期等类型                                      |

→ 建议 **.xlsx**，但需要你确认「允许新增一个前端依赖」。若不许，退路是「CSV + 每表一个文件，打进一个 ZIP」，用现有 `localSave.ts` 的 ZIP 链路。

### 10.5 P2-② · 新增「方向」分区（已完成）

**为什么新增一个分区**：方向（`AssetCollection` 树）是数据本体的骨架，但它原先只能通过左树导航
与「新建方向」按钮间接管理 —— 改名、改归属、删层级，以及每个方向的参与方式与输出目录，
都没有集中的编辑入口。这一区把「方向结构」与「方向级参数」两张表摆在一起，补的正是
§一 缺口 1 里那类断层。

| 表       | 列                                                                      | 行主键         |
| -------- | ----------------------------------------------------------------------- | -------------- |
| 方向结构 | 名称 / 层级 / 上级 / 子项 / 加子项 / 删除                               | `collectionId` |
| 方向参数 | 方向路径 / 设置来源 / 参与产出 / 输出目录（带选目录按钮）/ 水印（只读） | `collectionId` |

三条口径：

1. **行序 = 左树的深度优先顺序**（`buildDirectionRows`）：表格与树对不上号是最容易改错行的地方；
2. **参数表显示生效值**并单开「设置来源」列（本级 / 继承 / 全局）说明它是哪来的 ——
   只显示本级值会让「空着」被误读成「什么都不产出」，实际是向上继承；
3. **含成环保护**：`上级` 列的候选项排除自己与全部子孙（`collectSubtreeIds`），
   遍历带 `visited` —— 一个 `parentId` 互指就能让整个工作区白屏。

### 10.6 P2-③ · 方向 × 水印归属表（已完成）

原先「哪几个方向在用哪几套水印」只能靠左树节点上的覆盖计数徽章逐个点开看。
新增归属表（`ConsoleWatermarkBindings`，行主键 `collectionId:presetId`）：

- **只列显式声明过的归属**。没写过的方向沿用全局默认，不出现在表里 ——
  否则「全局清单」会让每个方向都长出一行，表格立刻失去信息量；全局默认在表下写明。
- **两种删除语义分开给两个按钮**：「移除」= 写不含该项的数组（**空数组 = 显式不加水印**）、
  「改为继承」= 写 `undefined`（不表态）。`resolveNodeWatermarkBinding` 对这两者有刻意区分，
  界面上只差一个字、语义完全不同，用一个按钮表达不了。
- **悬空引用（预设已删）不隐藏**，标注「已删除」，否则用户永远不知道要清理。

### 10.7 执行中推翻的两个方案判断

**① 分发配置（区域 ⑩）不做表格化。**
方案里把它列为 A 档「键值表」，实际实现时判断**不该做**：它是单例配置而非数据集，
10 个字段里 7 个是布尔开关，做成「一行一个字段」的两列表格是**伪表格** ——
既不如现在的中文标签表单可读，也拿不到表格的任何好处（比较、排序、批量）。
「适合以表格呈现」里的「适合」是判据。它导出时仍会进一张 Sheet，导入导出能力不受影响。

**② 尺寸表的行粒度被反馈改掉了（对方写线，2026-09-21）。**
我实现的是「一行一个规格」（渠道当外键 + 可跨渠道移动）；随后收到反馈**改成「一行一个渠道」**，
渠道行内展开它的尺寸。方案 §二 ③ 描述的字段结构仍然成立（宽 / 高 / 体积上限 / 启用 / 方向），
只是行粒度不同。**记录在此以免后续按旧方案去对账**。
