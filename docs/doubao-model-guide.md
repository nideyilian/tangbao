# 豆包模型（Seedream / SeedEdit）使用规范与方法

- 适用范围：糖包生图链路里"模型名带 `doubao` / `seedream` / `seededit`"的那一类模型
- 落地版本：`TB-150`（2026-10-08）
- 依据：`src/lib/openaiCompatibleImageApi.ts` 的 `isArkImageModel` / `callArkImageApi` + `.workbuddy/memory/2026-10-08.md` 的中转实测

---

## 0. 一句话

**糖包内置了豆包（火山方舟形状）的独立请求分支 —— 只要模型名里带 `doubao` / `seedream` / `seededit`，就会自动走这条分支，不需要额外选服务商、也不用手改请求形状。**

代价是这条分支**比 OpenAI 通道窄**：只认方舟文档化的少数字段，尺寸有像素下限，遮罩局部重绘不支持。

---

## 1. 怎么配

### 路线 A：内置通道（推荐，零配置）

1. 设置 → 模型接口 → 服务商选 **OpenAI 兼容接口**（内置的 `openai`）
2. `API URL` 填你的上游地址（官方方舟或你的中转）
3. `API Key` 填 Key
4. **模型名**填带豆包前缀的名字，例如 `doubao-seedream-4-0-250828` / `Doubao-seedream-4.5` / `Doubao-Seedream-5.0-lite`

配好后糖包会自动识别 → 走方舟形状发请求。**无需任何其它开关。**

> ⚠️ 识别只看**模型名**。模型名写成 `seedream-4.0`、`Seedream`、`seededit-3.0` 都命中；写成 `4.0`、`db-4.0` 之类不含关键词的名字则**不会**命中，会按 OpenAI 形状发（那条路对豆包必失败，见 §7）。

### 路线 B：自定义服务商（上游形状不标准 / 需要 apiProxy 时）

若你的中转是严格的 OpenAI 形状（`/images/generations` 不接 `image` 字段、未知字段报 400），内置分支可能对不上，此时走「自定义服务商」：

- 配置模板已备好：`.workbuddy/doubao-provider-import.json`（本机文件，不进 git）
- 导入入口：设置 → 模型接口 → 服务商下拉 → **创建自定义服务商** → **从剪贴板粘贴并导入**
- 导入后需**手动补一次 API Key**（新 profile id 没有对应密钥）
- 本地地址（如 `127.0.0.1`）在**生产版**会被 CSP 拦，需打开该服务商的 `apiProxy`（走主进程转发）

## 3. 尺寸规范（最容易踩的一格）

### 3.1 硬规则

- **方舟只认像素值或 `1K`/`2K`/`4K` 关键词。** 糖包 UI 的 `auto` 一律**不发** `size` 字段（交给服务端默认）。
- **方舟对生成图有总像素下限**，低于下限上游直接拒绝。
- 糖包 UI 的 1K / 2K / 4K 档位 + 比例会自动换算成像素，换算表见 §3.3。

### 3.2 实测结果（2026-10-08，经第三方中转）

| 模型 | 尺寸 | 结果 |
| --- | --- | --- |
| Seedream 4.0 | `1024x1024` | ✅ |
| Seedream 4.0 | `1536x1024` | ✅ |
| Seedream 4.0 | `1024x768` | ❌ 低于下限 |
| Seedream 4.0 | `2048x2048` | ✅ |
| Seedream 4.5 | `1024x1024` | ❌ |
| Seedream 4.5 | `2160x1440` | ❌ |
| Seedream 4.5 | `2560x1440` | ✅ |
| Seedream 5.0-lite | `2048x2048` | ✅ |

**读法：4.0 的下限约在 `1280x720`（921,600 px）一档；4.5 的下限明显更高，约在 `2560x1440`（3,686,400 px）一档。**

> 未实测的格子不要想当然。**换模型 = 重新核对尺寸。**

### 3.3 糖包档位 → 像素对照表

| 比例 | 1K | 2K | 4K |
| --- | --- | --- | --- |
| 1:1 | 1024x1024 | 2048x2048 | 2880x2880 |
| 3:2 | 1536x1024 | 2160x1440 | 3456x2304 |
| 2:3 | 1024x1536 | 1440x2160 | 2304x3456 |
| 16:9 | 1280x720 | 2560x1440 | 3840x2160 |
| 9:16 | 720x1280 | 1440x2560 | 2160x3840 |
| 4:3 | 1024x768 | 2048x1536 | 3200x2400 |
| 3:4 | 768x1024 | 1536x2048 | 2400x3200 |
| 21:9 | 1280x544 | 2560x1088 | 3840x1600 |

### 3.4 糖包侧的尺寸口径

- 换算逻辑：`src/lib/size.ts` 的 `calculateImageSize(tier, ratio)`，16 倍数对齐，最大边 3840，比例误差容忍 1%。
- **1K 档的 `4:3` / `3:4` / `21:9`（1024x768 / 768x1024 / 1280x544）在 4.0 上确定会失败**（实测 1024x768 ❌）。
- 失败时糖包会在错误文案后追加一句尺寸提示（`1K 的 4:3 / 3:4 等小尺寸会被上游拒绝，建议改用 2K 档尺寸`）—— **看到这句就是尺寸问题，不用再查别处。**

**实操结论：豆包模型默认就用 2K 档，最省心。**

## 4. 图生图

- **文生图和图生图走同一个端点**：`POST {baseUrl}/images/generations`。
- **参考图进 JSON 的 `image` 数组**（URL 或 data URL），**不走 `/images/edits`**。
  - data URL 的格式段须小写：`data:image/png;base64,...` ✅ / `data:image/PNG;base64,...` ❌
- **参考图宽高必须 > 14px**（8x8 的测试图会被拒）。
- 请求体是 **JSON**，不是 OpenAI 那条 multipart 上传。

> 这也是为什么"只改模型名就能切豆包"必须在代码里做分支 —— 豆包没有 `/images/edits`，OpenAI 那条图生图路径对豆包**必然 404**。

## 5. 不支持的能力

| 能力 | 状态 | 说明 |
| --- | --- | --- |
| 遮罩局部重绘（mask） | ❌ **直接报错** | 提示「豆包（火山方舟）模型不支持遮罩局部重绘，请改用参考图模式，或换用其他模型。」**刻意不做静默降级** |
| `quality` | ❌ 不发 | 方舟不认，请求里一律省略 |
| `moderation` | ❌ 不发 | 同上 |
| `output_format` | ❌ 不发 | **带上会被上游拒绝**（中转会包装成"所有供应商暂时不可用"） |
| `n` | ❌ 不发 | 同上 |
| `output_compression` | ❌ 不发 | 同上 |

**方舟分支实际只发 6 个字段：`model` / `prompt` / `size` / `response_format` / `watermark` / `image`。**

其中 `watermark` **固定为 `false`** —— 方舟默认给图打「AI生成」水印，糖包显式关掉。

## 6. 提示词规范（⭐ 最要命的一条）

### 6.1 负向约束不能堆敏感词 —— 会让**全部**请求 503

2026-10-08 定案的真凶：糖包会把「信息流广告负向约束」拼接到 `prompt` 后面再发。
内置规则如果**枚举敏感词**（色情／毒品／赌博／未成年人／血腥／国家机关／伪造文件…），
**上游内容审核会把提示词本身判成违规** → 中转把它包装成 `503 所有供应商暂时不可用`。

实测证据（同一 Key、同一时刻直连）：

| 组合 | 结果 |
| --- | --- |
| 用户原文 + 参考图 | ✅ 200 |
| 用户原文 + 负向约束 + 参考图 | ❌ 503 |
| 用户原文 + 负向约束（无参考图） | ❌ 503 |
| 仅负向约束 + 参考图 | ❌ 503 |

**已修复**：三条内置规则（通用严格 / 今日头条 / 广点通）改写为**不枚举敏感词的抽象表述**，
位置 `src/types.ts:278` 的 `DEFAULT_AD_NEGATIVE_RULE_PROFILES`。

### 6.2 用自家规则时别退回枚举写法

自定义负向约束写"禁止出现 XX、YY、ZZ"这种敏感词清单，**在豆包上就是把整条链路关掉**。
正确姿势：写**抽象约束**，例如「画面内容健康向上、专业清晰，符合商业广告的通用审核规范」。

## 7. 报错对照表

| 看到的报错 | 真实原因 | 怎么办 |
| --- | --- | --- |
| `HTTP 503: No available providers` / 「所有供应商暂时不可用」 | 上游拒绝了请求（**含内容审核**），中转统一翻译成这句话 | 先怀疑**请求内容**（prompt 有没有敏感词堆叠 / 负向约束），不要以为是"没渠道" |
| 错误文案后跟着「建议改用 2K 档尺寸」 | 尺寸低于模型像素下限 | 升到 2K 档 |
| 「豆包（火山方舟）模型不支持遮罩局部重绘」 | 用了 mask | 改参考图模式，或换模型 |
| 图生图 404「上游未找到对应端点」 | 请求走到了 `/images/edits`（说明模型名没命中方舟分支） | 核对模型名是否含 `doubao`/`seedream`/`seededit` |
| 400 参数错误 | 上游形状与预期不符 | 改走自定义服务商（§1 路线 B） |

> ⚠️ **中转会把上游 400 参数错误、内容审核拒绝统统翻译成 503「所有供应商暂时不可用」** —— 极难判断真因。看到这句先自查请求内容与尺寸，别先怀疑网络。

## 8. 与 OpenAI 通道的差异总表

| 维度 | OpenAI 兼容通道 | 豆包（方舟）分支 |
| --- | --- | --- |
| 触发方式 | 默认 | 模型名命中 `/doubao\|seedream\|seededit/i` |
| 文生图端点 | `/images/generations` | 同左 |
| 图生图端点 | `/images/edits`（multipart） | **同一个 `/images/generations`（JSON `image` 数组）** |
| 请求体 | multipart / JSON | 纯 JSON |
| `output_format` | 发 | **不发** |
| `quality` / `moderation` / `n` | 发 | **不发** |
| `watermark` | 无此字段 | 发，固定 `false` |
| 遮罩重绘 | 支持 | **不支持（直接报错）** |
| 尺寸 `auto` | 可发 | **不发** |

## 9. 技术实现（改之前先看这里）

| 位置 | 作用 |
| --- | --- |
| `src/lib/openaiCompatibleImageApi.ts:528` | `ARK_IMAGE_MODEL_PATTERN = /doubao\|seedream\|seededit/i` |
| `src/lib/openaiCompatibleImageApi.ts:530` | `isArkImageModel()` 判定 |
| `src/lib/openaiCompatibleImageApi.ts:561` | `callArkImageApi()` 请求实现 |
| `src/lib/openaiCompatibleImageApi.ts:543` | 分派顺序：**自定义服务商 → 方舟分支 → `apiMode` 分派** |
| `src/lib/api.test.ts:489` | `describe('火山方舟（豆包）模型适配')`，5 条守卫用例 |
| `src/lib/size.ts` | 档位/比例 → 像素换算 |

**改动的三条纪律：**

1. 方舟分支**只在 `customProvider` 之后、`apiMode` 分派之前**插入 —— 这是刻意的顺序，别调。
2. 新增字段前先确认方舟认不认；**多一个字段就可能让整条链路 503**。
3. **`getActiveApiProfile` 里顶层 `settings.model` 会覆盖 `profile.model`**（`apiProfiles.ts:948`），
   写测试时两处都要设，否则生效的还是默认的 `gpt-image-2`。
