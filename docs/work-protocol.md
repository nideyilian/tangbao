# 协作与写线协议（work-protocol）

> 适用于本仓库的**所有**参与者：杰哥 + 所有 AI 会话（WorkBuddy / CodeBuddy / 终端 / 其他工具）。
> 这不是建议，是**资源独占条件下的必需约定** —— 违反它的直接后果是事故，不是效率下降。

## 一、为什么需要

**24 小时内 3 次「无法生图」级事故，全部由并行引起**（证据在 `docs/RISK.md` R-01）：

| 事故                     | 根因                                                                            |
| ------------------------ | ------------------------------------------------------------------------------- |
| 生成卡在提示词阶段       | 另一条工作线的改动经 **HMR 整页刷新**打断了运行中的窗口                         |
| 窗口空白、点什么都没反应 | 两个会话反复 `npm run dev`，**41731 端口 + 单实例锁互抢**，先起的实例被静默杀掉 |
| 3 条快照数据被写坏       | 写库没带 `record_id`，一把梭覆盖（**这与并行无关，属操作纪律**）                |

**物理约束（不可绕过）**

- `vite` 固定 `127.0.0.1:41731`（`strictPort`）
- Electron 单实例锁按 `userData` 独占
- `localStorage` leveldb 被应用进程独占 `LOCK`（外部脚本改不了）
- HMR 会把**任何**改动热更新进**所有**正在使用该 dev server 的窗口

## 二、核心原则：单写线

> **同一仓库同一时刻只允许一条写线。**

写线 = 有一条会话正在改代码 / 跑 dev / 改数据。

**开工前必须做的三件事**

1. 确认 41731 是否已被占用：`netstat -ano | grep 41731`
2. 若已占用 → 查明是谁（父进程链：`bash → npm run dev → cmd → vite`），**不要抢，也不要反复重启去"救"窗口**
   （dev server 一死窗口不会自恢复，但抢来抢去只会互相顶掉）
3. 确认另一条线在改哪些文件（`git status`），与本次影响面**有重叠就停下来先解决冲突**

## 三、真并行：用 worktree 物理隔离

需要两条线同时推进时，**不要**在同一目录开两个会话。

```bash
# 并行线（示例）
git worktree add ../TANGBAO.wt-watermark -b feat/watermark
```

| 会话   | 目录                       | vite 端口     | userData                      | 说明                                                 |
| ------ | -------------------------- | ------------- | ----------------------------- | ---------------------------------------------------- |
| 主写线 | `D:\AAA\TANGBAO`           | 41731（默认） | `%APPDATA%\tangbao`           | 唯一可直接跑 dev 的线                                |
| 并行线 | `D:\AAA\TANGBAO.wt-<主题>` | 41800+        | `%APPDATA%\tangbao-wt-<主题>` | 改 `vite.config.ts` 端口 + 用环境变量指独立 userData |

**并行线的纪律**

- 只提交自己 `git status` 里确认过的文件 —— **禁止 `git add -A`**
  （曾发生：开工时发现工作区里另有一条不属于本轮的未提交改动）
- 合并回主写线时走 PR 或 `git cherry-pick`（两仓无共享历史时只能 `fetch` + `cherry-pick`）
- 并行期间**不要**对外发版本

## 四、会话交接三件套

AI 会话没有跨会话记忆，所以交接**必须靠文件**。

**开工读三处**

| 顺序 | 文件              | 看什么                                     |
| ---- | ----------------- | ------------------------------------------ |
| 1    | `AGENTS.md`       | 规范（代码风格 / 设计系统合规 / 发布流程） |
| 2    | `docs/BACKLOG.md` | 在途表 + 目标 TB 的验收标准                |
| 3    | `docs/RISK.md`    | 与本任务相关等级的条目                     |

**收工写三处**

| 顺序 | 动作                                                                                   |
| ---- | -------------------------------------------------------------------------------------- |
| 1    | `docs/BACKLOG.md`：TB 状态改 `DONE` + 填**验收证据**（commit / 测试数 / 实测数字）     |
| 2    | `docs/RISK.md`：踩到新坑当场登记（不要只写日志 —— 日志会被压缩，风险登记册是长期资产） |
| 3    | 当日 `.workbuddy/memory/YYYY-MM-DD.md`：只记**过程与判断依据**；硬结论一律外迁         |

> **日志与登记册的分工**：日志是"这件事是怎么走到这里的"（可被压缩），
> 登记册是"下次必须知道什么"（不可被压缩）。

## 五、角色边界

| 角色       | 谁      | 职责                                              | 禁止                                                     |
| ---------- | ------- | ------------------------------------------------- | -------------------------------------------------------- |
| 产品负责人 | 杰哥    | **唯一决策者**：拍板范围 / 验收 / 版本 / 是否开工 | —                                                        |
| 执行       | AI 会话 | 实现 TB、写测试、跑验证、记录证据                 | 不擅自扩大范围；不擅自改 `AGENTS.md`；不替用户改全局配置 |
| 记录       | AI 会话 | 维护 BACKLOG / RISK / runbook / ADR               | 不改写历史结论（只追加，或标注"已过期"）                 |

**正面范例（照这个模式做）**

> 杰哥四项拍板：「手动入口保留 · 多水印需要 · 分发保留移植 · 不自动归档」→ AI 落地。
> AI 只提问不代替决策，杰哥拍板、AI 执行。

**必须交给杰哥定的事（AI 不得自行决定）**

- 全局启用范围（`selectedMediaIds` / `selectedCollectionIds`）
- 用户数据的批量改写
- 版本号与是否发布
- 需求范围本身（"要不要做"）

## 六、开工 / 收工清单

**Definition of Ready**（满足才动代码）

- [ ] `BACKLOG.md` 里有 TB 编号，验收标准**写得能测**（不是形容词）
- [ ] 无其他写线在跑（`netstat` 查 41731）；影响面与其他线无重叠
- [ ] 已看 `RISK.md` 中相关条目
- [ ] 涉及持久化 / 数据库 → 先做备份（`backup-before-*`）

**Definition of Done**（任一条不满足即不算完成）

- [ ] `npm run verify` 全绿
- [ ] `npx prettier --write` 已跑（`AGENTS.md` 硬要求）
- [ ] `BACKLOG.md` 状态 + 验收证据已更新
- [ ] 架构级决策 → 补一条 `docs/adr/`
- [ ] 新坑 → 登记 `RISK.md`，配方 → 写进 `docs/tangbao-ops-runbook.md`
- [ ] **已提交并推送**（不留未提交改动过夜）
- [ ] 对外可见 → 更新 `RELEASE.md`

## 七、数据操作纪律（改用户数据 / 数据库时）

1. **停应用**（否则 leveldb 与 SQLite 都被锁）
2. **备份**到 `%APPDATA%\<app>\backup-before-<事项>-<时间戳>\`，保留不删
3. 写库**必须带 `record_id` 条件**；编码按 namespace 分两种（zustand 型双重 / 记录型单层）
4. 基线**一律用 `readOnly: true` 读**（带残留 WAL 时读写连接可能读到 0 条 → 会把"合并"做成"覆盖"）
5. 改完**回读校验** + 全库编码体检
6. 完整配方见 `docs/tangbao-ops-runbook.md`

**结论**：协议生效 —— 本次交付**零 `src/` 改动**，全程没有打断运行中的 dev。

最省事的是**先停掉 dev 并明确告知**，而不是让执行方去赌"HMR 不会打断正在跑的生成任务"。
