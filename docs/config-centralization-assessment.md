# 「集中配置常量」评估报告

> 2026-09-20 · 杰哥诉求「目前很多常量是隐藏起来的，需要用户自己去代码里修改，我希望把这些都集中在
> 某个配置文件，让用户可配置」· 本轮只评估，不改代码。

## 结论先行

| 你的描述                 | 评估结论                                                                                                                                                                                  |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 「很多常量是隐藏起来的」 | **对，但不是全部该开放**。实测 177 个导出常量 + 151 处魔数，其中**只有 34 个（19%）是「默认值」形态**，天然可配；28 个是内部/协议标识（不该开放）；115 个是算法与 UI 细节（多数不该开放） |
| 「集中在某个配置文件」   | **同意，但要做成分层的三档**，不是一个大文件 —— 不然配置文件自己会变成新的「藏起来的地方」                                                                                                |
| 「让用户可配置」         | **需要区分「用户可配置」与「开发者可调」**：全开放会让 177 个常量变成 177 个支持工单的来源                                                                                                |
| ⚠️ **最关键的一条**      | **本需求与 TB-050 参数重构有交叠但不等同**，两者必须**排先后**，否则会做两遍                                                                                                              |

**一句话**：值得做，但要先想清「开放给谁」。**我的建议是：只把「影响产出结果 / 影响成本 /
影响本机环境」三类做成用户可配置，其余保持代码常量**（详见 §四）。

## 二、关键分歧：这个需求不是「一个配置文件」能解决的

### 2.1 三类常量的性质完全不同

| 类型               | 例子                                   | 用户该不该改      | 改错的后果             |
| ------------------ | -------------------------------------- | ----------------- | ---------------------- |
| **A. 产出结果类**  | 命名模板、产出尺寸、水印预设、压缩质量 | ✅ **应该开放**   | 产出错误素材（可察觉） |
| **B. 本机环境类**  | 输出目录、API 端点、密钥、代理地址     | ✅ **应该开放**   | 功能不可用（可察觉）   |
| **C. 算法/协议类** | 重试次数、退避基数、并发上限、缓存大小 | ⚠️ **谨慎开放**   | 静默劣化 / 触发限流    |
| **D. 内部实现类**  | hover 延迟 150ms、防抖 400ms、动画时长 | ❌ **不该开放**   | 纯噪声，用户不会改     |
| **E. 安全边界类**  | IPC 白名单根、CSP、可信渲染进程校验    | ❌ **绝不能开放** | **R-62 就是这么来的**  |

> ⚠️ **E 类要特别说明**：`electron/ipc-handlers.ts` 的 `getAllowedRoots` 是安全边界。
> 刚才那个 bug（TB-049 / R-62）的根源就是「业务需求想要 D 盘，安全策略只放行文档目录」。
> **如果做成「用户可以配置白名单根目录」，等于把安全边界交给用户，等于没有边界。**
> 正确做法仍然是 TB-049 的方案 A：**从用户已配置的输出目录反推受信根**，而不是让用户直接改白名单。

### 2.2 所以「集中在某个配置文件」的正确答案是**三个不同层**，不是一个文件

```
┌─ 第一档：用户配置（运行时可变，有 UI，可导入导出）────────────┐
│  现状：local-settings.json + zustand persist（已有）           │
│  内容：输出目录 / API 配置 / 命名模板 / 渠道规格 / 主题        │
│  ⚠️ 这一档不是「新建」，是「把散落的补进来」                    │
└───────────────────────────────────────────────────────────────┘
┌─ 第二档：可调常量（有默认值，高级设置里可改，不常动）──────────┐
│  ★ 本次要新建的：src/config/tunables.ts                        │
│  内容：C 类（重试、退避、超时、并发、缓存上限）                 │
│  形态：带默认值的对象 + 校验 + 越界夹紧（clamp）                │
└───────────────────────────────────────────────────────────────┘
┌─ 第三档：代码常量（不开放，但集中声明便于查阅）────────────────┐
│  ★ 本次要新建的：src/config/constants.ts                       │
│  内容：D 类（UI 时序）+ E 类（安全边界，只读）                  │
│  形态：纯 `export const`，用途是把「藏在函数体里的魔数」提出来   │
└───────────────────────────────────────────────────────────────┘
```

**关键点**：第三档**仍然不是用户可配的**，但它解决了你的一半痛点 ——
「要找某个魔数，去一个文件里找」而不是 grep 整个代码库。

## 三、为什么不建议「全部开放成配置文件」

三个具体风险，都有本仓先例：

1. **静默失效家族**（R-07 / R-47 / R-63）：一旦常量可配，就必须回答「配错了怎么办」。
   现有三个静默失效点都是这个模式。若把 151 处魔数全开放，等于新增 151 个潜在静默点。
2. **支持成本**：177 个常量全开放 → 用户改坏 → 报障「不产出图片」→ 排查第一步变成
   「先确认你没改过高级设置」。**当前 TB-049 的排查链路已经够长了**。
3. **与安全边界冲突**：见 §2.1 的 E 类。开放安全类常量＝拆除防护。

## 四、建议方案（分两步，先小后大）

### Step 1（小、低风险、可立刻做）：把魔数提出来集中声明

- 新建 `src/config/constants.ts`（D 类 + E 类的**只读**声明）
- 新建 `src/config/tunables.ts`（C 类，带默认值 + 描述 + 校验）
- **行为零变化**：只是把散落的字面量换成一个具名常量，配合 `grep` 可查
- **验收**：`verify` 全绿 + 新增一条守卫测试，禁止 `setTimeout` 用裸数字（可做棘轮）

> 这一步不会让用户「可配置」，但**解决了「找不到」**，且**零行为风险**。

### Step 2（大、需裁决）：把 A / B 类接入「统一设置中心」

这一档**与 TB-050 高度相关**——TB-050 要把参数收成「全局模块 + 索引表」，
正好是承载「用户可配置项」的位置。**两者应该合并做，而不是各做一遍。**

建议的归属：

| 配置项                         | 归属                          | 对应 TB     |
| ------------------------------ | ----------------------------- | ----------- |
| 输出目录 / 命名模板 / 渠道规格 | 参数中心（TB-050 的索引表）   | TB-050      |
| API 端点 / 密钥 / 代理         | 设置 → 服务商（已有）         | —           |
| 白名单受信根                   | 由输出目录**反推**（自动）    | TB-049      |
| 重试 / 退避 / 超时（C 类）     | 设置 → 高级（可选，折叠深处） | 本次 Step 2 |

## 五、待杰哥裁决（3 点）

### 裁决 1：开放范围

- **A（推荐）**：只开放 A/B 类（产出结果 + 本机环境），C 类进高级设置，D/E 类只集中不开放
- **B**：A/B/C 全开放
- **C**：全部开放（不推荐，理由见 §三）

### 裁决 2：与 TB-050 的先后

- **A（推荐）**：**先做 Step 1**（提魔数，零风险），**Step 2 合并进 TB-050**（一次做对，不重复改界面）
- **B**：本次独立做完 Step 2，TB-050 之后再改一遍

### 裁决 3：C 类要不要暴露

C 类（重试/退避/超时）**不开放也能活**，但开放有真实价值（网络环境差的用户能救自己）。
是否值得为它加一个「设置 → 高级」页？
