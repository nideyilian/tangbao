## 一、结论先行

**可行性：可行，且比你预想的收益更大 —— 因为「自动备份」压根不是一个独立功能，而是两套互不知情的机制拼出来的。**

| 判断                            | 结论                                                                                    |
| ------------------------------- | --------------------------------------------------------------------------------------- |
| 收敛为「导出 / 导入」两个功能   | ✅ 可行。现有 ZIP 链路能力已完全覆盖另外两套                                            |
| 自动备份「移除 or 并入导出」    | ✅ **建议并入**（不是移除）。理由见 §4.3 —— 它现在是唯一真·自动机制                     |
| 默认只导必要数据、任务/图片可选 | ⚠️ **可行，但要区分「手动导出」和「定时备份」两套默认**，否则定时备份会失去意义（§4.1） |
| 默认导出密钥                    | ❌ **建议改为默认不导出**。明文密钥 + 不加密 ZIP 的组合风险过高（§3.1）                 |

**最大的发现：所谓「三个功能都经常失效」，根因不是三个功能各自有 bug，而是它们互相打架。** 见 §2.3。

## 二、现状：三套机制并存（带证据）

| 机制                           | 存什么                                                                                                                                       | 存到哪                                         | 谁触发                                                                                    | 重叠                        |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------- | ----------------------------------------------------------------------------------------- | --------------------------- |
| **A. ZIP 导出/导入**（主链路） | manifest v7 + settings(可含密钥) / tasks / sopPromptRuns / agentConversations / 素材库 / 工作区 / compositeState；可选原图、缩略图、合成资源 | 用户自选（默认 `库根/backups/`）               | 手动 `SettingsModal:4282` + 首启提醒 `App.tsx:349` + **每周自动 `App.tsx:382`（写桌面）** | **能力最强，覆盖 B 与 C**   |
| **B. 旧版 JSON 数据文件**      | tasks / agentConversations / 图片**元数据**（无二进制）                                                                                      | 用户下载 JSON                                  | 仅手动 `SettingsModal:3953` → `LegacyDataImportModal`                                     | 与 A 完全重叠               |
| **C. Electron 状态文件快照**   | `userData/tangbao.json` 的快照（设置、草稿、收藏夹、工作区标签）**不含任务图片**                                                             | `userData/backups/tangbao-<ts>.json`，留 30 份 | 自动：每次写状态时，间隔 600 分钟 `ipc-handlers.ts:1450`                                  | 与 A 的 `exportConfig` 重叠 |

### 2.1 三个「名不副实」的点（需要先纠正认知）

1. **`userData/backups/` 一直是空的，是因为设置页「备份列表」读的是 C，而每周自动备份（A）写的是桌面。**
   → 用户在设置页看到的备份列表，和自动备份产生的文件**根本不在同一个目录**。
   证据：`localSave.ts:1001`（列表读 `dataPath+'/tangbao.json'` 的备份目录）vs `App.tsx:379-381`（写 `getDesktopPath()`）。
2. **设置页文案说「备份默认保存到素材库的 `backups/`」（`SettingsModal:4312`），但自动备份实际写桌面** —— 文案与实现不符。
3. **`createBackupInPath`（`localSave.ts:1019`）是死代码，全仓无调用方** —— 这是「手动创建备份」入口被删后的残留。

### 2.2 还有两个 backups 目录并存

- `userData/backups/` —— C 的状态文件快照
- `库根/backups/` —— ZIP 导出的默认目录（`ipc-handlers.ts:533`）

两者语义不同、目录不同、保留策略不同，UI 上却都叫「备份」。

### 2.3 ⭐ 为什么「经常无法正常生效」—— 根因

不是随机 bug，是三个可复现的设计缺陷：

| #     | 根因                                                  | 证据                                                                                    | 表现                                                     |
| ----- | ----------------------------------------------------- | --------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| **1** | **原图缺失 → 整包导出失败**，无部分导出降级           | `store.ts:11567-11568`（浏览器）、`11656-11657`（Electron）：只要有一张原图读不到就抛错 | 勾选「包含原始图片」时导出频繁失败，用户只看到"导出失败" |
| **2** | **导入无事务回滚**，失败前已写入的 tasks / 素材不撤销 | `store.ts:11958`、`12064` 只在 catch 里 toast                                           | 导入失败后数据处于**半吊子状态**，比导入前更糟           |
| **3** | **自动备份失败用户无感**                              | `App.tsx:400-402` 仅 `console.warn`；`ipc-handlers.ts:1457` 仅 `console.error`          | 用户以为有备份，实际一次都没成功过                       |

补充：非 Chromium 浏览器 >256MB 直接失败（`store.ts:11369`）；无冲突提示，只有事后 toast 报数（`12201-12222`）。

## 三、风险评估（按你点名的四项）

### 3.1 🔴 密钥明文存储与安全性 —— **最高风险，建议改变你的默认值**

**现状**：

- 平时存储是**安全的**：Electron `safeStorage` 加密，文件 `userData/api-secrets.bin`（`electron/secure-api-secrets.ts:43`），**非明文 SQLite**。
- 导出包内：`includeSecrets=true` 时是**明文 JSON**；**ZIP 不加密、无密码**（`exportZipToPath` 无加密参数，`localSave.ts:1064`）。
- UI 已明示「包含 API Key（明文，谨慎使用）」（`SettingsModal:4264-4271`）。

**风险**：一个不加密的 ZIP 里躺着全部 API Key。它会被丢到桌面（自动备份）、被 QQ/微信传、被上传网盘。

**我的建议（与你的方案不同，请裁决）**：

| 方案                         | 做法                                                                                | 评价                                  |
| ---------------------------- | ----------------------------------------------------------------------------------- | ------------------------------------- |
| ① **默认不导出密钥**（推荐） | 默认只导配置骨架；密钥勾选后才导，且勾选时**强制二次确认 + 明确列出将包含几个 Key** | 换机成本 = 重新填一次 Key；安全性最高 |
| ② 导出密钥但 ZIP 加密码      | 需引入密码输入与 ZIP 加密（当前 `exportZipToPath` 不支持）                          | 改造量大，且用户会忘密码              |
| ③ 按你的原方案默认导出       | 保持现状默认勾选                                                                    | ❌ 不建议                             |

> 关键取舍：**密钥的"必要数据"属性是弱的** —— 换机重填一次的成本，远低于密钥泄露的成本。而 SOP、项目树、收藏提示词才是真正不可重建的资产（丢了就没了）。
> → 我建议「必要数据」定义为：**配置骨架 + SOP + 收藏提示词 + 项目树 + 个人设置**，**密钥默认排除**。

### 3.2 🔴 导入的覆盖与冲突 —— **当前是"薛定谔的覆盖"**

**现状**：是否整体覆盖取决于一个隐晦条件 ——
`store.ts:11987-11991`：`version>=5 && workspaceState 存在 && importConfig && importTasks` 时 `replaceWorkspace=true`，
此时 tasks / agentConversations / workspaceTabs **整体替换**；否则走 merge。

**问题**：

- 用户**无法预期**这次导入是覆盖还是合并（取决于包的内容 + 两个复选框的组合）
- 无任何冲突提示，只有事后 toast 报数
- **失败不回滚**（见 §2.3 #2）

**改造方案**：显式三选一 + 预演 + 回滚

| 模式             | 语义                                                 | 适用         |
| ---------------- | ---------------------------------------------------- | ------------ |
| **合并**（默认） | 按主键去重追加，已存在的不动                         | 日常         |
| **覆盖**         | 整体替换所选槽位                                     | 换机恢复     |
| **仅恢复配置**   | 只导 settings + SOP + 项目树 + 收藏，不动 tasks/素材 | 配置被搞坏了 |

并且：

1. **导入前 dry-run 预览**：解析 manifest → 列出"将新增 N 条任务 / 覆盖 M 个配置 / 跳过 K 个已存在"，用户确认后才写库
2. **失败可回滚**：把当前状态先落一份临时快照，导入异常时 restore（这是把 C 机制的思路反过来用）
3. **冲突可视化**：同名 SOP / 同名收藏夹要能选择"保留本地 / 用导入的 / 两个都要"

### 3.3 🟡 导出文件大小控制 —— **默认不含任务/图片后，问题基本消失**

按你的方案，默认只导配置 + SOP + 收藏 + 项目树 → **预估几十 KB ~ 几 MB**，ZIP 完全无压力。

剩余风险点（任务/图片可选开启时）：

- 原图是**存储模式不压缩**（`store.ts:11610`，因为已是压缩格式）→ 包大小 ≈ 原图总大小
- 非 Chromium 浏览器 >256MB 直接失败（`store.ts:11369`）
- mtime 越界需特判（`store.ts:11241`）

**建议**：

1. 导出前**预估大小并展示**（扫一遍待导出的图片字节数），超过阈值提示关闭原图
2. 开启原图时，**容忍部分缺失**：缺 N 张就跳过 N 张并在结果里报数，**不再整包失败**（这是修 §2.3 #1 的关键）
3. 缩略图默认含、原图默认不含（缩略图小且够用于预览）

### 3.4 🟡 旧版本数据兼容 —— **必须向后兼容，不能一刀切**

**现状**：manifest `version: 7`（`store.ts:11571`）。历史备份 v3~v7 都在外面。

**风险**：收敛后若改 manifest 结构，老备份导入失败 = 用户唯一的数据救命稻草断了。

**建议**：

1. **保持 `version: 7` 不变**，新增字段一律可选（现有 `ExportData` 除 `version`/`exportedAt` 外全可选，这个设计很好，继续沿用）
2. 新增一个 `profile` 字段标记"这是精简版导出（config-only）"还是"完整导出"，**老包没有该字段 → 按完整包处理**
3. 导入器必须能读 v3~v7；v7 之前的 `normalize*` 逻辑不要删
4. **B 机制（旧版 JSON）下线时保留导入能力至少一个大版本**，不要同时删导出和导入（用户手里还有旧 JSON 文件）

### 3.5 🟢 补充风险：与另一个会话的冲突（已规避设计）

见 §5。

## 四、整合改造方案

### 4.1 目标形态

```
设置页 · 数据管理
├─ 导出                    ← 合并原「导出数据」+「每周自动备份」
│   ├─ 默认槽位（不可取消）：个人设置、SOP 数据、收藏提示词、项目树、水印预设
│   ├─ 可选项：API 配置与密钥（默认关）、任务与对话、原图、素材库
│   └─ 定时备份开关（默认开，每 7 天一次，落到 库根/backups/）
└─ 导入                    ← 合并原「导入数据」+「备份列表恢复」+「导入旧版数据」
    ├─ 选文件（ZIP / 旧版 JSON 自动识别）
    ├─ 预演：展示将新增/覆盖/跳过多少
    └─ 模式：合并（默认）/ 覆盖 / 仅恢复配置
```

### 4.2 关于「默认不含任务」—— 我的不同意见 ⚠️

你的原话是「任务和图片数据体量过大，默认不纳入导出包」。**这个对「手动导出」成立，但对「定时备份」会导致备份形同虚设**：

- 定时备份的目的是**灾难恢复**（配置被重置那次就是典型场景，TB-030）
- 如果定时备份默认不含任务 → 恢复后只有配置、没有任务 → **等于没备份**

**建议：两套默认分开**

| 场景         | 默认包含                                         | 理由                                                                 |
| ------------ | ------------------------------------------------ | -------------------------------------------------------------------- |
| **手动导出** | 配置 + SOP + 收藏 + 项目树（不含任务/图片/密钥） | 你提的诉求：轻量、可频繁做                                           |
| **定时备份** | 上面 **+ 任务与对话**（不含原图、不含密钥）      | 灾难恢复必须有任务；不含原图所以体积可控（对话+任务元数据通常几 MB） |

### 4.3 自动备份：**并入导出，不要移除**

理由：C 机制（`userData/backups/` 的状态文件快照）是**目前唯一真正在自动跑的保护**，也是配置被重置那次唯一可能救回来的东西。直接移除会让数据保护能力下降。

**并入后的做法**：

| 项                   | 现在                                                                      | 改为                                                                           |
| -------------------- | ------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| 落地路径             | **桌面**（`App.tsx:379`）                                                 | **库根 `backups/`**（与设置页文案一致，也符合 M20「复制库根 = 完整备份」心智） |
| 触发                 | 每周一次，仅在启动时求值                                                  | 同上（启动 + 7 天间隔已够用，不引入定时器复杂度）                              |
| 内容                 | 写死 `{exportConfig, exportTasks, exportImages:false, exportAssets:true}` | 复用「定时备份」选项组，用户可改                                               |
| 保留策略             | **无**（桌面会堆一堆 zip）                                                | 保留最近 **10** 份，超出自动清理                                               |
| 失败可见             | `console.warn`，用户无感                                                  | **toast + 状态落到 store**（`lastAutoBackupAt` / `lastAutoBackupError`）       |
| 状态文件快照 C       | 保留（它便宜且与 ZIP 互补：写状态即快照，间隔 600 分钟）                  | 保留，但**从 UI 上合并展示**：备份列表同时列出 ZIP 与状态快照                  |
| `createBackupInPath` | 死代码                                                                    | 删除                                                                           |

## 五、与「水印预设导出导入」的边界（另一个会话）

**已核实的现状**：

- 水印预设 `presets` 在 `compositeV2` store 的持久化字段里（`storeV2.ts:153`）

**边界划分建议**：

| 层                                                                                                                             | 谁负责         | 说明                                                                         |
| ------------------------------------------------------------------------------------------------------------------------------ | -------------- | ---------------------------------------------------------------------------- |
| 预设的**序列化/反序列化/合并**（`getCompositeV2PersistedState` / `replaceCompositeV2PersistedState` / `mergeImportedPresets`） | **另一个会话** | 我不碰 `features/composite/**`                                               |

**唯一需要对齐的一点**：我在 §4.1 把「水印预设」列入默认导出槽位。如果另一个会话做的是**独立的预设导出文件**（区别于整包），那两者是并列的两个功能，不冲突；但如果他们期望预设**不随整包导出**，就需要你裁决。

**建议**：预设随整包走（`exportConfig` 已包含，零改动），独立预设导出作为补充 —— 两套并存、互不干扰。

## 六、改造后如何保证「稳定生效」

光改功能不够，必须有可验证的闭环。这套东西之所以"经常失效"，一半原因是**没有任何一处能证明它成功了**。

### 6.1 让失败可见（治 §2.3 #3）

| 项       | 做法                                                                                          |
| -------- | --------------------------------------------------------------------------------------------- |
| 导出结果 | 落 store：`lastExportAt` / `lastExportResult`（成功 + 条目数 / 失败原因）                     |
| 自动备份 | 落 store：`lastAutoBackupAt` / **`lastAutoBackupError`**；失败时 toast，不再只 `console.warn` |
| 导入结果 | dry-run 预览必须在写库前展示；失败时**自动回滚**并明确告知"已恢复到导入前状态"                |

### 6.2 必须有自动化验证（当前几乎为零）

现状：导出/导入**几乎没有单测覆盖**（本次调研未见 `exportData` / `importData` 的测试文件）。这是"经常失效"能被容忍到今天的根本原因。

**建议补的测试**（每条对应一个已知失效模式）：

### 9.2 ⭐ P3 执行中发现并修掉的**严重连带缺陷**

把 `exportTasks` 默认改为 `false` 时发现：`replaceWorkspace` 的判定是

```
version>=5 && workspaceState 存在 && importConfig && importTasks
```

**它没有检查「包里是否真的带了任务」** → 导入一个「只导配置」的包（任务默认不纳入）时该条件仍成立，
本地 `tasks` 会被**整体替换为空** —— 用户任务被一次配置导入静默清空。

已补上 `(preflightData.tasks?.length ?? 0) > 0`。用户要清空任务有专门的「清除数据」。

> 这个缺陷**在改动默认值之前就一直存在**（只要用户取消勾选任务导出即可触发），
> 属于本次调研顺带发现的历史隐患。

### 9.3 一个值得记的现象：测试通过，但走的是另一条路径

`dataExport.test.ts:155` **早就有** `skips missing image records instead of aborting the whole export`
——纯函数层保证了「跳过缺失原图」，但 `store.ts` 层在那个计划之后又直接 `throw`。
于是**测试全绿、用户却导出失败**。

→ 教训：**调用链上的每一层都要为同一个承诺负责**；测试只覆盖叶子函数时，
中间层加一句 `throw` 就能让承诺失效，而门禁完全看不出来。
